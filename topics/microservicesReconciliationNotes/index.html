    Reconciliation Notes — Microservices Guide¶

    Internal working notes, not part of How Teranode's Microservices Work.

    While writing that guide, statements were checked against the code rather than against the existing documentation. This file records where reality differed from expectation, where the existing documentation and the code disagree, and where the code has plumbing that nothing currently uses.

    Nothing here is a claim that the guide is wrong. It is a list of things a reader of the guide would otherwise reasonably assume, plus a few loose ends for maintainers.

    Read this file top to bottom once; afterwards it is a lookup table.

    Conventions¶

    Every entry carries file and line references so each claim can be re-checked rather than trusted. Line numbers refer to the working tree at the time of writing and will drift.

    Entries are marked:

    • Confirmed — code agrees with expectation; noted only because it is surprising.
    • Divergence — code and existing documentation say different things.
    • Gap — the code offers a mechanism that no caller uses.
    • Judgement call — the guide simplifies in a way the reader should know about.

    Decisions taken¶

    Recorded because a future reader meeting only the findings would otherwise reasonably propose the opposite.

    • Nothing in these findings is to be ported into existing project files. The discoveries below — dependency levels, the FSM guard, the reputation-versus-ban distinction, the overloaded use of "level" — stay in the two new documents. The existing documentation set is left exactly as it is, contradictions and all, and is not amended to agree with the guide. Where the two disagree, this file is the record of the disagreement.
    • Where the examples disagree, the guide treats the production-shaped deployment as "as shipped". Sections 25 and 26 establish that teranode-cr.yaml is a development fixture, and that teranode-cr-mainnet.yaml and the Docker overlays agree with each other. Scaling commentary now says which of the two it means, rather than averaging them. This is a reasoning choice, not an instruction from a maintainer — open question 8 keeps the underlying question live.
    • Both new documents stay off the site navigation. Deliberate for now, not an oversight. Neither is listed in mkdocs.yml, so neither appears in the built site. Worth being explicit about, since a page sitting in docs/ is easily mistaken for a page that has been published.
    • For the interfaces, "published contract" means reading the files, not listing their names. Section 76 finds two of the eight contract files deliberately misnamed (services/propagation/ClientInterface.go, services/blockassembly/Interface.go:66), so every count in the interfaces section came from reading interface declarations rather than from a filename search. The same choice made the Legacy contract visible: it sits a directory deeper than the convention implies (services/legacy/peer/Interface.go), which a survey by filename reports as "Legacy publishes nothing".
    • A door counts as unauthenticated only if its server start proves it. Section 78 is argued from the last argument passed to each StartGRPCServer call — nil for five services, an options block without a key for a sixth — rather than from the absence of a middleware line. Propagation is the reason for the strictness: it builds an auth options block, which reads as "authenticated" until the shared installer is checked (util/grpc.go:83-88 requires either a default-deny flag or a non-empty key, and Propagation supplies neither).

    This means section 7 describes an overlap that is being left in place, and section 8 describes a naming collision that is being left unresolved except by the disambiguation line in the guide. Neither is awaiting a fix. The deployment reading in sections 25 to 29 is the one place this pass changed the guide's own wording rather than only recording a disagreement: the guide had the front door listed as wholly unresolved, and the evidence in this tree settles which door ships even though the intent behind it stays an open question. The interfaces work moved the guide's prose in two places for the same reason. Part One used "is this transaction valid?" as its example of a phone call, and section 81 shows that question answered without a phone call in the shipped configuration — Part One now says the example describes the design rather than the default. And the interfaces section first described the eight Validator replicas as reached through the Kubernetes door, which section 81 shows they are not: they are fed by the conveyor belt, which is why the topic carrying that work is given thirty-two partitions in the same settings file.

    1. An invalid subtree costs a peer reputation, not ban score¶

    Confirmed, and the asymmetry is easy to get wrong.

    When subtree validation rejects a bundle, the complaint reaches P2P and is charged against the responsible peer. The natural assumption — which the first draft of the guide made and which is wrong — is that the peer gets banned.

    It does not. The charge is one recorded failed interaction:

    • ReportInvalidSubtree — services/p2p/Server.go:3273 — resolves the offending peer and finishes by calling UpdatePeerMetrics(... recordFailure=true ...), then returns nil. No ban score is touched.
    • UpdateMetrics — services/blockchain/peer_registry.go:474 — increments InteractionAttempts and InteractionFailures, then recalculates the reputation score.

    Reputation is computed at services/blockchain/peer_registry.go:688: baseline 50, weighted 60% toward success rate, minus 15 for a failure within the last hour, plus 10 for a recent success, scaled by a response-speed factor. A peer marked malicious is pinned at 5, and the code comments make explicit that no other factor redeems it.

    The asymmetry worth flagging¶

    An invalid block does attract ban score:

    • processInvalidBlockMessage — services/p2p/server_helpers.go:939 — charges ReasonInvalidBlock through AddBanScore.

    An invalid subtree does not. The same event class, two different penalties.

    This looks deliberate rather than accidental. The comment above the reputation call reads: "This will not be too harsh on failures of transient behavior but also track if we are having trouble fetching data from peers" (services/p2p/Server.go, in ReportInvalidSubtree). A subtree can fail to validate because a piece went missing in transit, which is a network fault and not an indictment of the peer. A whole block arriving corrupt is harder to blame on the network.

    Worth confirming with the maintainers that this is intended policy and not a wiring oversight, because it is the kind of thing that reads as a bug.

    2. ReasonInvalidSubtree is defined and never charged¶

    Gap.

    ReasonInvalidSubtree = "invalid_subtree" is declared at services/p2p/ban_reasons.go:13 and admitted to the allowlist at services/p2p/ban_reasons.go:38.

    No production code path passes it to AddBanScore. Every caller in the tree:

    • services/blockvalidation/BlockValidation.go:2738 — ReasonCorruptBlockBody
    • services/p2p/server_helpers.go:939 — ReasonInvalidBlock
    • services/p2p/Server.go:3095 — applyBanScore, generic helper, reason supplied by caller

    So the constant exists, the penalty-point lookup on the Blockchain side is built to accept it, and nothing fires it.

    Care needed when reading the allowlist: knownBanReasons is a Prometheus cardinality guard, not a usage inventory. The comment at services/p2p/ban_reasons.go:31 explains that its job is to stop an unrecognised incoming reason minting unbounded metric series. An entry appearing there means "this reason is a recognised label value", not "this reason is enforced". Grepping that map for evidence of behaviour will mislead.

    Consequence: if someone later wires subtree failures through AddBanScore, the allowlist and penalty configuration already accept the reason, so the change is one call site.

    3. "Horizontally scalable" needs two answers, not one¶

    Confirmed; existing documentation already says so, and this guide's first draft did not.

    Subtree validation is built as a stateless worker drawing from a Kafka topic, which is the pattern that divides across instances cleanly. As shipped, it runs one instance.

    From deploy/kubernetes/teranode/teranode-cr-mainnet.yaml: every service that is enabled is pinned to replicas: 1 except the Validator at replicas: 8 (line 183). The general teranode-cr.yaml pins everything to 1.

    That needs one correction, which this file got wrong on first pass. replicas is not the whole deployment story, because several services in the same file carry enabled: false and so run zero instances — among them the P2P service itself. "One copy" and "the example does not deploy it" are different statements about the same component. See section 9.

    This means that for most services, throughput available today comes from intra-instance parallelism across the cores of one machine, not from a fleet. Widening is a deployment decision rather than a rebuild, but it is not switched on.

    teranode-microservices-overview.md carries the same caveat in its introduction, so this is a correction to the new guide's first draft, not to the existing set. Recorded here because the two documents must keep saying the same thing.

    Where the bottleneck is expected¶

    The Validator at eight replicas, against one of everything else, is a load-bearing hint about operator expectations: signature checking is the anticipated constraint. It also means the guide's per-service scaling notes are incomplete on their own — subtree validation sorts work into parallel levels and then hands the heavy arithmetic to the Validator, so effective scaling is a property of the pair.

    4. Who gets blamed for a bad bundle is a real problem, not a formality¶

    Confirmed, and understated by the existing documentation.

    A subtree is typically announced by one peer and served by another. The comment at services/p2p/Server.go in ReportInvalidSubtree states the situation plainly: subtrees are "announced by the miner that built them but served invalid by whichever peer's DataHub the block came from". Charging the announcer for a defect in bytes it never sent would penalise an innocent party.

    Three behaviours follow, all of which the guide now describes:

    • Attribution resolves through the DataHub URL the bytes were actually fetched from, to the peer registered as its owner.
    • Where no serving peer can be identified, nobody is charged and the function returns successfully. Under-information produces restraint, not a guess.
    • Announcer-versus-server mismatch is logged at info level rather than silently reconciled.

    Related, and separately useful: bans are held in their own ledger and survive a peer disconnect on purpose. Remove() at services/blockchain/peer_registry.go:485 keeps the ban-score entry, with the comment that otherwise "an offending peer could clear its own ban simply by reconnecting".

    5. The FSM guard prevents a specific and unattractive failure¶

    Confirmed; not mentioned in the existing service documentation.

    Peer-announced subtrees are only validated while the Blockchain service reports RUNNING — services/subtreevalidation/subtreeHandler.go:62.

    The comment explains why the check is not simply "is the service up": an IDLE state can follow an operator STOP partway through catch-up, leaving a node holding a UTXO set far behind the tip. A node in that position lacks the information to judge whether a bundle is valid, and would confidently reject honest peers' data.

    Worth stating in operational terms, since the consequence is uneven: a node restarting mid-catch-up without this guard would turn against healthy connections at exactly the moment it most needs them.

    6. Judgement calls made in the guide¶

    Points where the guide simplifies, so a maintainer is not surprised:

    • "Roughly every ten minutes" for block arrival is the nominal target, not a guarantee.
    • Subtree structure is described as transactions "stacked above" their dependencies. Accurate enough for the dependency-levels argument, but it omits padding rules and the leaf-count policy check at services/subtreevalidation/check_block_subtrees.go:1696.
    • Subtree validation is described as producing "receipts" for downstream services. These are txmeta records published to Kafka, whose actual shape is the meta.Data struct at stores/utxo/meta/data.go:32 — transaction, inpoints, block heights, fee, size, locktime, coinbase flag, unmined marker.
    • Memory handling is attributed to three habits: streaming rather than bulk loading, arena pooling, and early release. All three exist — services/subtreevalidation/arena_pool.go, readTransactionsFromSubtreeDataStream at check_block_subtrees.go:1162, and explicit early-nil hints in processTransactionsInLevels at check_block_subtrees.go:1230. Their relative contribution is not measured in the guide and is not claimed.
    • Duplicate suppression for complaints refers to the de-duplication map in publishInvalidSubtree at services/subtreevalidation/Server.go:1017. The window is one minute — an expiring map constructed at services/subtreevalidation/Server.go:204. The guide does not state the window.

    For the P2P section:

    • Announcement size caps are stated as ten kilobytes for a block and eight for a transaction bundle, from maxBlockMessageSize and maxSubtreeMessageSize at services/p2p/Server.go:119. Both are compile-time constants, not operator settings; the guide implies the same and should not be read as describing a tunable.
    • "Fair share" eviction in the bounded announcement-attribution map is described qualitatively. The mechanism is documented in detail at the head of services/p2p/capped_peer_map.go, including the two issue numbers behind the design (1409 for inline bounding, 1503 for the fair-share direction) and an explicit statement that cross-peer washout is bounded rather than eliminated. The guide keeps that caveat but does not quantify the residual.
    • The multi-publisher budget is described as "a handful". The actual default is seenHashMaxPublishersPerHash in services/p2p/seen_hash_cache.go, operator-tunable via p2p_seen_hash_max_publishers. The guide is deliberately vague about the number and explicit that the value is configurable.
    • "Reputation at or above 20" is the literal viability floor at services/p2p/sync_coordinator.go:193. Worth knowing that this is a hard-coded constant rather than a setting, and that a peer marked malicious is pinned at reputation 5 by calculateAndUpdateReputation — so the malicious flag excludes a peer from sync selection indirectly, by driving the score below the floor, not through a separate check.
    • The three-kinds-of-progress discussion compresses two distinct mechanisms into one narrative: the no-progress stall deadline refreshed only from peer-attributable delivery, and the backoff multiplier that deliberately does not de-escalate on local tip advance. Both are documented with their full reasoning in resetProbeBudgetIfLocalChainWorkAdvanced at services/p2p/sync_coordinator.go:434. The guide's shorter version does not mention the probe budget itself, which is a third bounded quantity.
    • Pruned-peer fallback is described as picking "the youngest" peer. That matches the setting description at settings.conf:1082 — smallest lag, to limit the damage from coin records already discarded — and is gated by p2p_allow_pruned_node_fallback, default true.
    • "A single peer identifier, key and connection set" in the scaling section is a paraphrase of per-instance configuration keys such as p2p_peer_id and p2p_private_key, and of the indexed p2p-1 instance in compose/docker-compose-ss.yml:204. The guide does not claim multiple P2P instances run in any shipped Kubernetes configuration.

    7. Documentation overlap¶

    The new guide sits alongside material that already covers some of the same ground, differently:

    • docs/topics/architecture/teranode-microservices-overview.md — per-service responsibilities, endpoints, interaction diagrams.
    • docs/topics/services/subtreeValidation.md — detailed reference. Covers subtree handling, pause coordination and Merkle level calculation, but does not mention dependency levels, the FSM guard, or the reputation-versus-ban distinction.
    • docs/topics/architecture/understandingDoubleSpends.md — conflict and reorg handling, which the guide defers to rather than restating.

    No contradiction found between these three and the guide's Subtree Validation section. The gap is additive: the mechanisms in sections 4, 5 and 6 above are absent from subtreeValidation.md. They will stay absent — see Decisions taken — so a reader who needs them should come to this file rather than expecting the reference to grow.

    8. "Level" means three different things¶

    Divergence, or at least a collision waiting to happen.

    The guide explains that a bundle's transactions are sorted into dependency levels to enable parallel checking. The existing reference document uses the same word twice over for unrelated ideas:

    • Merkle tree levels — depth layers of the hash tree: leaves, then 500 intermediate nodes, then 250. Discussed at docs/topics/services/subtreeValidation.md:198 under "Level Calculation for Merkle Trees", where the stated purpose is memory pre-allocation.
    • Two-Level Checking — a name for the pause-flag lookup pattern at docs/topics/services/subtreeValidation.md:172: fast atomic boolean locally, then a distributed lock check. Nothing to do with either of the other two.

    The three are unrelated in substance:

    Term Sorts what Purpose
    Merkle tree levels Hash nodes Memory pre-allocation
    Two-Level Checking Two ways of reading one flag Cheap pause detection
    Dependency levels Transactions, by what they need Ordering, so checking parallelises

    The collision matters practically because a reader trying to confirm the guide against the reference document will find "level" documented, and may conclude the mechanism is the Merkle one. It is not. Worth either renaming in one of the two documents, or stating the distinction explicitly in both.

    The guide now carries a one-line disambiguation in the Subtree Validation section.

    9. The two example cluster configurations disagree about what runs¶

    Divergence, and the more consequential finding in this file.

    deploy/kubernetes/teranode/ ships two examples. They are not two sizes of the same deployment; they disagree about which services exist.

    Service General teranode-cr.yaml teranode-cr-mainnet.yaml
    P2P (peer) enabled disabled
    Validator disabled enabled, 8 replicas
    Legacy disabled enabled
    Propagation disabled disabled
    Block Persister disabled disabled
    UTXO Persister disabled disabled
    Bootstrap disabled disabled
    Coinbase disabled disabled

    Three observations:

    • The file named for mainnet does not run the service that talks to the network, and runs the compatibility layer instead. The modern mesh is off and the legacy Bitcoin protocol path is on. That is a coherent choice, but nothing in either file says so, and it is not the arrangement a reader would predict from the filenames.
    • The general example does not run the Validator, which the guide's own scaling discussion identifies as the anticipated bottleneck and the only component scaled out in the other file. Read alone, the general example suggests validation is not deployed at all.
    • Block Persister and UTXO Persister are disabled in both. Nothing in either example enables the two services that file blocks and maintain the coin-set checkpoint, so neither example is a complete deployment on its own terms. Whether persistence arrives by another route in these topologies or the flags are simply stale cannot be determined from the YAML.
    • Propagation is disabled in both, and that one has a customer-facing edge. Old-protocol submitters are unaffected — the Legacy door takes transactions itself — but an HTTP submitter posts to the asset server's /tx route, which is registered and forwards to a service with no instance running (section 13). The read side of the same public address works normally, which is what makes the gap quiet.

    Read with section 25, which establishes that these are not two production shapes but a development fixture and a production shape, and section 26, which brings in the Docker examples that section 9 did not consult. The table below is still accurate; two of its framings are not.

    Practical consequence for anyone using these files as a starting point: the safe assumption is that neither is a working mainnet deployment as written, and the sensible next step is to confirm the intended service set with the maintainers.     12. Nothing in this tree appears to send work to Propagation¶

    13. The transaction door is advertised, the service behind it is not deployed¶

    Configuration divergence a customer would notice.

    Both example cluster configurations set propagation.enabled: false — see the table in section 9 — while settings.conf:234 keeps asset_propagation_proxy_enabled = true and :238 gives it a working cluster address for the .operator context. The asset server registers the proxy routes on the strength of the flag and a non-empty address, with no probe of whether anything is listening (services/asset/httpimpl/http.go:399-405).

    So as the examples stand, a wallet posting a transaction to the node's public address is forwarded to a service with no running instance and gets 502 Bad Gateway, counted by the asset server's own proxy counter (services/asset/httpimpl/propagation_proxy.go:24-28, :52-53, :270-275). That is the correct failure mode — loud, and measured — and it is worth saying so rather than implying the request vanishes. The read side of the same public address (GET /tx/:hash and friends, registered at services/asset/httpimpl/http.go:395-397) is served locally and works normally, which is what makes the gap easy to miss from outside: half the API is healthy.

    The proxy is a plain httputil.ReverseProxy (propagation_proxy.go:16-29), which matters for section 3 of these notes in a good way: a reverse proxy copies the backend's response headers, so the X-Teranode-Error verdict survives the extra hop and still reaches the customer.

    Two readings of the disabled flag, and the code cannot decide between them. Either real deployments take transactions some other way (the legacy door, which accepts old-protocol submissions and needs neither propagation nor this proxy), or these example files have drifted. Recorded as a question for a maintainer; the guide says the same thing in plain language rather than picking a side.

    15. The broadcast lane's size limit is 512 bytes, and its comment says 100 MiB¶

    Misleading constant, wrong by five orders of magnitude.

    maxDatagramSize = 512 // 100 * 1024 * 1024 (services/propagation/Server.go:79-80). The comment is stale; the value is what the code uses — it sizes the receive buffer for the IPv6 multicast listener (:496), which is the only thing the constant feeds.

    Consequence in operation: a transaction larger than the buffer arrives shortened, fails to parse as a wire message, and is dropped with a warning (:499-535). There is no metric for this — the metrics in this service count batches, single transactions, invalid transactions and admission rejections (services/propagation/metrics.go:76-138), and nothing counts UDP receipts at all. So on a machine where the broadcast lane is quietly losing every large transaction, the evidence is a warning line per loss.

    Recorded because the comment states the opposite of the behaviour, and the number that matters — how big a transaction this lane can carry — is exactly what someone would look up in a hurry.

    16. An unauthenticated door used to be able to buy a consensus shortcut¶

    Security finding, fixed in layers, with the residual written down by the fix itself.

    Issue 4840, finding B-022. The validator's HTTP /tx endpoint installs no authentication middleware (services/validator/http_options_guard.go:5-7), and until recently a caller posting there could set the same options an internal service can: skip script validation, skip policy checks, spend by outpoint without a hash check, suppress metadata publication, claim the transaction arrived inside a block — and assert the block height to validate against.

    The height is the lever, as the guard's own comment puts it: an asserted low height satisfies the below-checkpoint guard by construction, so the fast path that skips script execution opens up on a live transaction. services/validator/Server.go:970-974 now answers any behaviour-changing field with a 400 that names it.

    Three layers exist now, and the code is unusually precise about what each one buys:

    • The server route refuses options and accepts transaction bytes only (services/validator/Server.go:959-981).
    • The client refuses before transmission, so this version of the software is not itself a route for those flags — "it does not make the property hold generally", because "an un-upgraded validator still parses the old query string for anyone who asks" (services/validator/Client.go:721-733).
    • The fast path is bounded independently by the node's own chain tip, not the asserted height: "The guard above bounds the height the CALLER asserted; an attacker simply asserts a low one" (services/validator/Validator.go:1448-1471).

    Two things worth surfacing for anyone reading the guide's Validator section:

    • The real boundary is topology, not this guard. The guard file says the gRPC listener is also unauthenticated on the shipped profile (security_level_grpc defaults to 0, no auth interceptor), so the guard "removes the HTTP route rather than removing the capability from unauthenticated callers". Whether a stranger can reach the validator's port decides the exposure, and validator_httpListenAddress = :${VALIDATOR_HTTP_PORT} binds every interface outside the dev context (settings.conf:1755-1756).
    • The fix has a maintenance contract, and it is the fragile part. Every behaviour-changing field of the request must be listed in nonDefaultValidationOptions; a new proto field that skips the listing "becomes a silent hole in this guard — the same hole issue 4840 (finding B-022) exists to close". Nothing in the build enforces that listing.

    Also recorded because it is the kind of detail that surprises integrators: the legacy non-protobuf request shape on the same endpoint drops an option it cannot express rather than rejecting it, while the protobuf shape rejects. The code says so and declines to change it — "Whether it should reject instead is a behaviour change, and is not made here" (services/validator/Server.go:947-957).

    17. Transactions can be accepted, then dropped, and the submitter cannot see it¶

    Config-and-code finding, quantifiable.

    The ingestion path answers "accepted" at Propagation, once the transaction is durably stored and queued for validation. Downstream of that promise, if the block-assembly hand-off is rejected for a full queue, the validator retries in place for a bounded window (validator_blockAssemblyShedRetryTimeout, 2s) and then drops the transaction — after reversing its coin-store work so the drop leaves no trace. The counter's own documentation spells the consequence: "Propagation has already returned success to the submitter by then, so these drops are silent from the client's point of view — this is the counter to alert on" (services/validator/metrics.go:196-200).

    A second, subtler variant is logged as a counter too: a block-context transaction accepted, unlocked and spendable, but absent from this node's mining template — "not mineable by this node until the next unmined reload, which nothing schedules", so a rising value means a manual reset would recover transactions this node is quietly failing to mine (services/validator/metrics.go:202-209). That is a revenue effect on the mining path, not a consensus one, and it is measurable rather than visible.

    Neither exists in the shipped configuration: shedding requires a bounded ingest queue, and settings.conf:354 sets blockassembly_maxQueueItems = 0, which makes the queue unbounded and the reject path unreachable. So the default posture trades these two silent failure modes for an unbounded in-memory queue, and the machinery that would have detected the first one is dark. Recorded with section 18, which is the same trade seen from the other side.

    18. The ingest backpressure controller ships switched off, twice over¶

    Config finding, and a pattern worth naming.

    validator_kafkaBackpressureEnabled = false in settings.conf:1761, on a line whose own comment says the setting is not alone: "Enable queue-age-driven Kafka ingest backpressure (also set blockassembly_maxQueueItems)". Since that second value is 0 (section 17), the controller would be half-blind if it were enabled: the queue-fullness predicate returns "no usable signal" whenever the reported cap is not positive (services/validator/kafka_backpressure.go:376-396), which settings.conf:1779 also states. So age-driven pausing is off by a switch, and fullness-driven pausing is off by arithmetic.

    What the machinery does when enabled is worth restating here because the guide leans on it: it pauses the validator's own Kafka fetch when block assembly's queue head has waited longer than 500ms and resumes below 100ms (settings.conf:1764-1767), caps any single pause at 30s, fails open after 3 consecutive failed reads, and arms a cooldown proportional to how long it was paused. An earlier revision suppressed backpressure for a whole pause window after a fail-open, which on an unbounded queue is 30 seconds of growth toward the memory exhaustion the feature exists to prevent; the comment names that defect (A6) and the divisor that bounds it.

    Two recurring properties show up here and deserve their own note because they appear in other services too:

    • The controller distrusts the number it measures with. The drain floor it subtracts from head age comes from block assembly's own report, clamped so a negative becomes zero, because a bad value there "could invert the control decision" and "a bad peer must not be able to steer it". A mismatch with the local blockassembly_doubleSpendWindow is logged once per distinct value and names the setting to align (services/validator/kafka_backpressure.go:264-277).
    • The same setting lives in two processes and the code knows which copy it may trust. The hand-off deadline is sized from this process's local copy of blockassembly_queueFullWaitTimeout, explicitly "a safety margin only and never a control decision", which is why that value is not self-reported the way the double-spend window is (services/validator/Validator.go:2272-2300). handoff_deadline_total is the counter that points at the skew when the copies disagree (services/validator/metrics.go:226-235).

    This is the same two-context settings trap already recorded for the P2P user agent, and now a third appearance. If a future section needs a cross-process setting to drive a decision, the established answer in this codebase is to have the owning service report it over the wire, not to read a local copy.

    19. The double-spend hold-back is off, and it was also a loop bound¶

    Config finding with an incident attached.

    double_spend_window_millis = 0 (settings.conf:776) means block assembly holds nothing back: the queue's eligibility filter lets a batch dequeue immediately, so a transaction is eligible for mining the moment it arrives. That is a throughput choice, and defensible — but the same value also disables a safety bound somewhere else, and the setting's name advertises only one of its two jobs.

    The queue drain during or after block movement is bounded twice on purpose (services/blockassembly/subtreeprocessor/SubtreeProcessor.go:6442-6472): a time bound so the drain only takes what existed when it started, and an item bound as a backstop. The comment records how both failed:

    • With the window at zero the time bound was computed as zero, and the queue's dequeue short-circuits its filter when the eligibility time is not positive — so the bound switched itself off. It is switched off in the shipped default today.
    • The item bound counted batches and compared against a length measured in transactions, with roughly a thousand transactions per batch, permitting about a thousand times the intended work.

    The consequence is in the comment verbatim: with ingest at line rate and neither bound firing, "the scaling-2 pod sat for 35+ minutes at 558 GB RSS inside this loop". The fix takes one clock reading for both branches, counts items, and dequeues as it goes so the queue length — and the validator's backpressure that reads it — stays honest during the drain.

    Two smaller points worth recording:

    • The key has no service prefix. Every other block-assembly knob is blockassembly_*; this one is double_spend_window_millis (settings/blockassembly_settings.go:41). An operator searching the config for the service name will not find the value that governs both the mining hold-back and that loop bound.
    • The queue-stats contract names the ceiling and the window as reported values, not local settings, because the two processes live in independent settings contexts (services/blockassembly/Interface.go:41-58). Section 18 found the validator honouring this; block assembly is where the contract is written down.

    20. Queue depth means two different things in two monitors of the same queue¶

    Not a contradiction, but it reads like one, and the difference is the useful part.

    Block assembly publishes ingest queue statistics, and two consumers interpret them differently on purpose:

    • For deciding whether upstream should pause, depth alone is declared unusable — "it cannot tell a queue that is draining from one that is stalled, since a large but falling depth needs no intervention while a small but static one does" — while depth as a fraction of the ceiling is usable, and is how the validator's fill predicate works (services/blockassembly/Interface.go:30-35).
    • For detecting a stalled consumer, depth is worse than unusable: "depth is the untrustworthy half of the pair", because in the incident on record the blocked handler was draining the queue from inside the branch that blocked it, so a low reading coincided with a wedged loop. The stall detector keys on staleness alone, whatever the queue holds (services/blockassembly/dequeue_stall.go:87-97).

    Same queue, same numbers, two questions: "should I stop sending" uses age and fractional depth; "is the consumer stuck" uses time since the consumer last checked in. Both rules are in the code with their reasoning attached, so the guide states both rather than picking one as "the" monitoring rule.

    Related, and worth noting as good practice: the stall threshold is deliberately not a setting — thirty seconds hard-coded, severity split so routine long blocks log quietly — on the stated grounds that "guessing at a number now is what the gauge exists to avoid". The companion gauge is the evidence that would justify making it configurable.

    21. Restarted pending sets depend on a timestamp column's resolution¶

    Cross-store behaviour finding.

    On start, block assembly reloads unmined transactions from the coin ledger, sorts oldest-first by CreatedAt, and validates parent chains, dropping any transaction whose parent did not come first — cascading to its descendants (services/blockassembly/BlockAssembler.go:2920-2937).

    The comment spells out the trap precisely: CreatedAt is stamped per transaction with no enforced gap, and its resolution is store-dependent — milliseconds on Aerospike, one second on SQLite, "its CURRENT_TIMESTAMP default emits YYYY-MM-DD HH:MM:SS". A parent and child created close together therefore routinely share a value, most of the time on SQLite. With an unstable sort, the child can be emitted first, parent-chain validation calls that invalid, and the family disappears from the mining set — no rejection, no customer-visible error, just transactions that are no longer candidates.

    The fix is a stable sort plus a pass that reorders only runs of equal timestamps so in-set parents precede children (stableSortUnminedByCreatedAt, orderEqualCreatedAtRunsParentsFirst, orderRunParentsFirst), leaving unrelated transactions in incoming order. Guarded by tests in services/blockassembly/unmined_sort_test.go and services/blockassembly/load_unmined_extsort_test.go.

    Recorded because the interesting property is not the bug, which is fixed and tested, but the shape: behaviour differed by backing store, so a test suite that runs only on SQLite was exercising the path where the failure is nearly certain, and production on Aerospike saw it rarely enough to look like a phantom. Any future tie-broken ordering over stored timestamps inherits the same hazard.

    22. The transaction library's definition of a coinbase was wider than the rule¶

    Dependency-behaviour divergence, fixed locally with the reason recorded.

    Block validation rejects a block whose first transaction is not the reward transaction, and the tidy way to write that is the transaction library's own predicate. This service does not use it, and the comment states why: the library's test is a disjunction that "also accepts a 0xFFFFFFFF sequence number in place of a null prevout index, admitting a transaction svnode rejects" (services/blockvalidation/quick_validate.go:292-294). It uses model.IsConsensusCoinbase instead.

    The failure mode is the expensive asymmetric one rather than the visible one: a block this node accepts and the rest of the network refuses. No error is raised locally, so the divergence only surfaces as a chain this node is alone on.

    Recorded as a class rather than a curiosity. A helper named IsCoinbase reads as a definition of a consensus rule, and it was a convenience predicate with a wider extension. Any other call site using the library version for a consensus decision inherits the same gap — worth a grep if that question ever comes up: grep -rn "\.IsCoinbase()" --include=*.go services/.

    Second instance of section 11's pattern, and the pattern is now the finding.

    24. Catch-up trusts peers in three stages, and each stage closes a different cheap lie¶

    Mechanism worth recording because the ordering is the security property.

    Catch-up asks strangers for long runs of blocks, so the cheapest attacks are the ones that cost the peer almost nothing to produce. The code has three distinct guards, and what is worth capturing is that each one is placed before the expensive step it protects:

    • A self-consistent low-difficulty chain. Header-fetch validation checks each header's proof of work against that header's own claimed difficulty, so a peer can invent a chain of trivially-easy blocks. Step 9.5 of catch-up recomputes the difficulty the rules required from the header chain and rejects that peer — before full blocks are fetched (services/blockvalidation/catchup.go:357-362).
    • A fork deeper than the chain can safely abandon. The limit is coinbase maturity, and the comparison operator carries the reasoning in a comment that derives it: a reorganisation of depth d invalidates a coinbase at height G when G >= H - d + 1, and for that coinbase to have been spent in the old chain needs G + CoinbaseMaturity <= H, "which has a solution only when d > CoinbaseMaturity. So d == CoinbaseMaturity is safe ... and > is the correct operator here, not >=" (services/blockvalidation/catchup.go:1034-1041, issue 4592). A one-character error on a safety boundary, now carried with its proof.
    • State churn for a fork that never happens. The mined-set reset on fork detection must run only after the fork-depth and secret-mining checks pass, otherwise "a peer merely announcing a deep or secretly-mined fork would un-stamp this node's own still-canonical txs for a fork that is then rejected, churning honest tx-mined state for no reorg" (services/blockvalidation/catchup.go:287-290, issue 1145).

    Two supporting details that are good engineering rather than bugs, recorded because they are the type of decision that gets undone by someone tidying up:

    • Concurrent per-subtree fetch failures are collected into a set keyed by peer and charged once at the end, specifically so CatchupFailures cannot exceed CatchupAttempts (services/blockvalidation/catchup.go:75-81). Two metrics sharing a denominator must agree on arithmetic.
    • A catch-up trip interrupted by this node's own reorganisation is reported as a service error so the peer is not charged (services/blockvalidation/catchup.go:62-65), and cleanup of temporary subtree files tracks committed-block dependencies at run scope rather than attempt scope, because per-attempt freshness cannot see that a freshly written hash became a dependency while the write was still asynchronous (services/blockvalidation/catchup.go:83-95, issue 4692).

    28. listen_mode is read by one service, and the other one says so out loud¶

    (services/legacy/peer_server.go:2157-2161, with the same note repeated at :3418 and :3494.)

    29. Why the persisters are switched off: one documented, one not¶

    Partly resolves the sub-question section 9 could not settle.

    Section 9 wrote that nothing in either example enables the two services that file blocks and maintain the coin-set checkpoint, and that whether this was intentional or stale "cannot be determined from the YAML". For block persister, three places say so in prose:

    • deploy/docker/mainnet/docker-compose.yml:78 comments the service out under the words uses lots of disk space.
    • The operator guide gives the number: archival mode needs several terabytes on mainnet and "is not needed for standard validation or mining" (minersHowToInstallation.md:180-181). It is an opt-in profile (:176), and the guide notes it writes in parallel with the pruner and leaves pruning behaviour unchanged.
    • The live coin set does not depend on it: spent outputs are pruned from the UTXO store after 288 blocks (settings.conf:790, global_blockHeightRetention = 288), which the howto restates as the default and warns against raising (minersHowToInstallation.md:166-169).

    So "nothing persists the chain" was the wrong worry, and the guide should not carry it. The chain is served from the block and subtree stores, the coin set lives in the UTXO store with bounded retention, and the persister is an archival add-on for indexers and explorers.

    What stays open is utxoPersister: disabled in both Kubernetes files, and not merely disabled but unlisted in every Docker compose file in the tree. No howto names it and no comment explains its absence. Its role — building and restoring the UTXO checkpoint used to seed a node — is described in its own package and nowhere in the deployment documentation, so a reader cannot tell whether seeding happens some other way in these topologies or the service is simply not deployed yet. That is the residual of section 9, and it is the one still worth asking about.

    30. A fresh node boots parked, and two documents disagree about whether it can be un-parked¶

    Divergence between an existing howto and the FSM transition table.

    A node with no stored FSM state does not start working. blockchain_initializeNodeInState (settings.conf:457-459) is empty in the default context and IDLE in both the operator and docker.m contexts, so every deployment this repository ships boots parked — which the comment explains as deliberate: "Production operator and single-node Docker contexts start in IDLE so a seed can be inspected before catchup begins." The sync howto agrees, calls the parked period an "inspection window", and tells the operator to start synchronisation with an explicit command (docs/howto/miners/docker/minersHowToSyncTheNode.md:196-223). It also warns that during that window two services have not bound their gRPC listeners, so their healthchecks report starting or unhealthy on a node that is behaving exactly as designed — a monitoring false alarm written into the deployment method rather than in the code.

    The divergence is in one sentence of that passage:

    Catch-up promotes the node to RUNNING after it reaches the active network's highest checkpoint. There is no transition from CATCHINGBLOCKS back to IDLE, so verify the seed first.

    The transition table says otherwise. STOP is declared with sources RUNNING and CATCHINGBLOCKS and destination IDLE (services/blockchain/fsm.go:34-40), and the stop script in the same howto set is documented as asking for exactly that: "stop.sh asks Teranode to enter IDLE state, then runs docker compose down" (docs/howto/miners/docker/minersHowToStopStartDockerTeranode.md:80, echoed at docs/howto/miners/docker/minersHowToInstallation.md:211). So the sentence denies an operator a transition that exists, is wired, and is exercised on every documented stop.

    Two readings, and the finding survives both. If the author meant "catch-up never reverts to parked on its own", that is true and is also enforced deliberately elsewhere — automatic catch-up and promotion both refuse to undo a parked state, so parking is an operator's choice and only an operator can undo it. But the sentence as written is about whether the operator can go back, and it says they cannot, which will change a decision: an operator told that catch-up is irreversible inspects a seed much harder before pressing the button than one told a stop is one command away. Neither reading is recorded anywhere an operator would find it.

    31. The peer opinion is not persisted in the shipped configuration¶

    Config gap, plus a setting whose own description overstates it.

    The Blockchain service holds the one opinion of every peer — reliability, catch-up success and failure counts, ban scores, ban expiry. That registry can be persisted: there is a versioned JSON envelope written to a fixed key in a configurable blob store, with ban scores and catch-up counters included, a save tick, and a load at startup that drops entries older than the configured lifetime (services/blockchain/peer_registry_persistence.go:16-46).

    It is switched off in everything this repository ships. Persistence activates only when blockchain_peerRegistryStore names a store, its default is empty (settings/blockchain_settings.go:34), and settings.conf contains no entry for it — nor for the save interval or any of the p2p_peer_registry_* keys, all of which therefore run at code defaults. The startup path logs the disabled state as a warning about the save interval rather than about persistence being off (services/blockchain/Server.go:555-561), and shutdown saves only if a store was constructed (Server.go:1071-1084), so with the shipped defaults the registry is memory-only even on a graceful stop. The consequence is concrete: every restart forgets who has misbehaved, and peers banned for bad data get a fresh allowance.

    The setting's long-form description calls a local on-disk store "default for single-node deployments". In the configuration that actually ships — which is a single-node deployment — it is not one. That phrasing will send a reader to look for a setting that is not there.

    32. One registry, two settings namespaces, and a floor derived from another service's constants¶

    Confirmed, and a maintenance hazard worth naming.

    The registry lives in the Blockchain service, and five of its knobs are split across two families: blockchain_peerRegistryStore and blockchain_peerRegistrySaveInterval in the BlockChain group, p2p_peer_registry_ttl, _max_size and _cleanup_interval in the P2P group (settings/settings.go:375-376, :601-603). Nothing groups them as one object, so an operator tuning peer behaviour has to know which half they are in.

    The TTL floor is worse, because its correctness is arithmetic spread over three constants in two services. A configured expiry below five minutes is raised to five minutes at startup (services/blockchain/Server.go:926-950). The number comes from: peers republish node status every ten seconds (services/p2p/Server.go:2034), the gossip batcher may coalesce those refreshes for up to a minute (services/p2p/peer_registry_batcher.go:31), and the floor is set at five times the batcher's window so a missed beat or two is survivable. Change the batcher's window and the floor's justification changes with it; no test or constant connects them. The documented failure if the floor were wrong is not mild: an actively-connected peer is evicted between its own refreshes, then fails the catch-up health check and is silently refused as a source of blocks.

    The handling is good — the coercion is logged rather than silent, and the setting's description explains the tuning hazard, unlike the two opt-outs (_max_size and _cleanup_interval) where zero is a documented permanent choice rather than a value to avoid. The gap is that the arithmetic is folklore in three files rather than one expression.

    33. The fast path is off, and the instrument watching it is armed behind it¶

    Config pair, and the third instance of a pattern this file has now named twice.

    Two settings govern the in-memory route that answers "is this block on the main chain?" without a database query. As shipped (settings.conf:466, :475):

    Setting Shipped Effect when set that way
    blockchain_use_in_memory_chain_check off route unused; every answer comes from SQL
    blockchain_chain_check_shadow_compare on compares accept decisions, samples rejects 1:1024

    With the route off, the comparison has nothing to compare: the code labels the SQL answer "the authoritative query already ran and produced this answer. Comparing it with itself measures nothing" (stores/blockchain/sql/CheckBlockIsInCurrentChain.go:112-113). So the watchdog is armed and dark, and it becomes live only if an operator turns the other knob — at which point, per the config comment, "enabling the route above with this left on measures no speedup; turning it off is what makes that fast path fast".

    The reachable trap is the ordering: the knob an operator finds first is the one that costs throughput. Turn on the fast path without turning off the comparison and the node takes the route's risk while paying the query the route existed to avoid. Section 18 and section 23 record the same shape — two settings where one is inert, misleading, or both until its partner moves — and this is the case where the shipped values are defensible and only the ordering is not.

    The comment also states an honest gap: the route is discouraged during initial sync because the insert path holds the main-chain guard for its whole length on a node with it enabled, and "the catch-up duty cycle where that starts to cost more than it saves has not been measured". So the shipped off is a measurement not yet taken, not a verdict.

    34. A stale "no" is another service's permanent decision¶

    Confirmed, and the clearest cross-service coupling in the service.

    The store's fast path can answer three ways: from the off-chain set by absence, from the high-water mark as "allocated but not yet committed", or from SQL. Each direction of error has a different cost, and the cost is not set by the store. Block validation asks this question when deciding what to do with an old block, and a negative answer is not a retry — it is an invalidation. The store's own comments carry that knowledge in five places, all naming the escalation: a false negative on a committed block "is escalated into a PERMANENT ValidateBlock invalidation; nothing undoes it until the two-minute background refresh happens to run" (stores/blockchain/sql/StoreBlock.go:328-336, and again at CheckBlockIsInCurrentChain.go:50-55, :130-137, :236-243, :354-360).

    That is why the awkward-looking behaviours exist. The high-water mark is advanced together with a rebuild that can observe the new block, never on its own, because advancing it alone would flip the error direction from "committed block reads as uncommitted" to "fork block reads as proven on-chain" — and the second one is the false positive that lets the asset server serve a merkle proof against a block that is not in the chain (:63-80). The mark of zero is not treated as initialised even though a genesis-only chain legitimately has a zero mark, because guessing the other way would mark every committed block dangling (:44-57). And the allocated-but-uncommitted reject, which looked safe enough to skip in the shadow comparison, is sampled at one-in-1024 precisely because the window it can be wrong in — between a commit and the mark being refreshed — is the one that ends in permanent invalidation (:129-149).

    The finding is not that any of this is wrong. It is that a rule in Block Validation decides how the store must behave, and the only place that connection is written down is in comments inside the store.

    35. The short-chain fallback guards one difficulty lookup, not the other¶

    Gap, narrow in reach, and acknowledged in the source.

    Difficulty for a new block is computed between two ancestors: the "suitable" block at the tip, and the suitable block 144 heights back (services/blockchain/Difficulty.go:23, :128, :143-155). The second lookup handles a short chain explicitly: if the ancestor is not found because the chain is too young, it falls back to the block's own hash and continues, while other failures — timeouts, database errors — are refused rather than fallen back on, because a silent fallback there "causes wrong difficulty".

    The first lookup has no such allowance, because it does not fail on a short chain; it fails after one. GetSuitableBlock walks up three ancestors and requires exactly three results, returning "not enough candidates for suitable block. have %d, need 3" otherwise (stores/blockchain/sql/GetSuitableBlock.go:106, :118-119, :180-181). On a chain of one or two blocks — a fresh chain, or a network seeded with less than three — the short-chain fallback hands that lookup a block with fewer than three ancestors, and difficulty becomes an error rather than a degraded answer. Whether that is reachable depends on how new a chain can be when assembly first asks, and nothing in the tree asserts it; the same function also answers a missing hash with "no result, no error" and a source comment asking whether it should be a not-found error instead (:125).

    36. Filing has a two-day fuse, and the fuse is the design¶

    Confirmed, and the load-bearing fact about this service.

    Nothing in the blob store is permanent merely because it was written. When Block Assembly files a bundle during assembly it stores the file together with a delete-at-height: the current coin-store height plus global_blockHeightRetention, which ships as 288 blocks — roughly 48 hours (services/blockassembly/Server.go:740, :891, :907; retention at settings.conf:790). Scheduling and cancelling are both performed through the Blockchain service's deletion scheduler, so there is one queue of pending deletions rather than one per caller (stores/blob/file/file.go:1171-1186).

    Block Persister's job is the cancellation. It sets delete-at-height to zero on the bundle and on the bundle structure once the filing copy exists, and zero is defined as "cancel the scheduled deletion", with the storage layer recording why that path is treated as critical: if cancellation fails, "the blob could still be deleted even though we want to persist it forever" (services/blockpersister/streaming_process_subtree.go:85-95, :231-233).

    Three consequences worth having stated together:

    • The window is the specification. A deployment without the persister does not lose anything that validation needs, and loses the entire archive without an error, because expiry is what the working copies were always supposed to do. That is why both Docker examples can comment the service out and still be honest about running a node.
    • The fuse is re-lit on rewrite. Where a bundle already exists, Block Assembly updates its delete-at-height rather than leaving the original date, so a bundle that keeps being written keeps being postponed (services/blockassembly/Server.go:889-896). Liveness of the archive therefore depends on write traffic as well as on the persister.
    • Being behind is a different failure from being absent. Once filing falls more than the retention behind, the transactions it needs to write into the archive have been pruned, and the failure surfaces as a per-transaction retrieval error rather than as "too far behind". Section 39 covers what the loop then does.

    37. The persister explains its coordination to the wrong service¶

    Divergence between code comments and code, in a comment written to prevent a race.

    Two long comment blocks in the persister describe a startup race and its fix — Block Assembly's cleanup could delete transactions the persister still needs, so the persister publishes its filed height at startup and again per block. Both comments name the consumer as Block Assembly: "BlockAssembler's cleanup service uses this to track how far we've progressed", "BlockAssembler reads this state during its startup initialization", and, most specifically, "See BlockAssembler.startChannelListeners for the notification handler" (services/blockpersister/Server.go:313-331, :398-410).

    Block Assembly does not do any of it. It has no reader for BlockPersisterHeight, no handler for NotificationType_BlockPersisted, and no startChannelListeners function. The consumer is the Pruner, which reads the same state key on startup (services/pruner/server.go:251-256) and handles the same notification to advance lastPersistedHeight (:156-176). Searching for the consumer from inside the persister lands a reader in a service that ignores both signals — and the comment is written in exactly the detail that makes it trustworthy, including the deletion bound formula.

    Worth noting on the other side: the arrangement the comments describe is sound, and the Pruner uses it correctly, including logging the moment the persister first reports a non-zero height (services/pruner/server.go:169-171). This is a stale pointer, not a broken mechanism. It is also precisely the kind of pointer that gets followed by someone debugging disk growth.

    38. The shipped single-node stack runs the deleter without the filer, on the trigger that waits for the filer¶

    Config gap, quantifiable, and the sharpest instance of the pattern in section 18.

    The Pruner supports two triggers, and the difference is which service proves a block is safe to prune from: OnBlockPersisted waits for filing, OnBlockMined waits for the mined-set flag and exists for deployments with no persister (services/pruner/server.go:140-144; setting documented at settings/pruner_settings.go:12 with the recommendation "Use OnBlockMined - Use when Block Persister is not available").

    The default is OnBlockPersisted (settings/settings.go:673), and pruner_block_trigger appears nowhere in this repository — not in settings.conf, not in the Docker compose files or their .env files, not in the Kubernetes examples. Meanwhile:

    Deployed in the single-node Docker stack State
    pruner runs
    blockpersister commented out
    pruner_block_trigger unset → OnBlockPersisted

    Walk the consequences through the code. Block notifications are ignored while configured for OnBlockPersisted (services/pruner/server.go:200-204). BlockPersisted notifications can only come from the persister (services/blockpersister/Server.go:408-417), which is not running. The startup catch-up pass reads the persisted height and acts only if it is above zero (services/pruner/server.go:251-256, :322-330), and that state is written only by the persister, so it stays zero. The code states the stall plainly in its own justification for retrying the header lookup: "in OnBlockPersisted mode there may be no subsequent notification to trigger pruning if this fails" (:326-329). With no persister the "no subsequent notification" case is not a risk at startup — it is the steady state.

    So as configured, the shipped stack starts a pruner that subscribes, reports itself healthy, accepts and executes deletions that were already scheduled, and never generates a new pruning pass. The visible symptom is not an error anywhere; it is the coin store growing.

    Two honest caveats. The supported install is a separate repository, so its .env may well set the trigger — that is unverifiable here and is the same limitation flagged in section 26. And with no persister there is nothing to file, so the archive is not the thing at risk; what is at risk is the disk bound the retention exists to provide.

    39. The retry pause guards the two branches that do not need it¶

    Gap, small, and directional rather than hypothetical.

    The persister's main loop has one sleep, blockpersister_persistSleep, shipped at ten seconds (settings.conf:292). It is applied on three branches: when the query for the next unfiled block fails, when there is nothing to file, and — a branch that makes the pattern look accidental rather than deliberate — when the block it just fetched cannot be serialised (services/blockpersister/Server.go:353-377). It is not applied when filing itself fails, which logs and starts the next pass immediately (:381-389), nor when the block cannot be marked as filed (:391-396) — the two branches most likely to fail for a reason that retrying sooner cannot fix.

    For transient trouble this is right — a store that hiccups should be retried at once, and the block will be filed on the next pass. The shape that is not covered is a block that cannot succeed. Section 36 describes how one arises: filing more than the retention window behind means the transactions the archive needs have already been pruned, and the retrieval fails with a per-transaction error (streaming_process_subtree.go:185, :202). That error is permanent until an operator intervenes, and the loop responds by re-querying the ledger, re-fetching from the coin store, re-reading the bundle structure and re-logging, back to back, indefinitely — with an error line each time, so the log grows as fast as the retries.

    The fix-shaped sentence is already in the code's vocabulary elsewhere in the deployment: retry with backoff after a failure that will not resolve by trying sooner, and pause at the shipped interval when the reason is that there is nothing to do. Today the pause is attached to the branch that needs it least.

    40. Three keys whose names point at a different service than the one that reads them¶

    Confirmed, and the third instance of the naming pattern in section 32.

    Each of these is consumed happily; the problem is what a reader looking for the knob, or an operator trying to predict an effect, is told.

    • utxoPersister_buffer_size is defined in the Block settings group (settings/block_settings.go:21, default 256KB) and read by three places: the file storer (services/utxopersister/filestorer/FileStorer.go:85), the coin-difference tracker (services/utxopersister/UTXOSet.go:522, :564, :714) and Block Persister (services/blockpersister/streaming_process_subtree.go:271). Nothing named "utxo persister" has to be running for it to matter.
    • blockpersister_skipUTXODelete is read in exactly one place, and it is in the UTXO Persister service (services/utxopersister/Server.go:568). Block Persister never reads it. Its shipped value is false (settings.conf:291), which happens to be the code default, so the mislabelling has no effect today — which is exactly when a name is cheapest to fix.
    • blockpersister_concurrency limits workers per block, and the inner batch parallelism inside each bundle is computed from processor count instead, ignoring the setting (streaming_process_subtree.go:123: four at minimum, half the cores otherwise). One knob governs the outer fan-out and silently does not govern the inner one.

    One small sharp edge in the same cluster, and it is worse than "a" fallback. A utxoPersister_buffer_size value that fails to parse is logged at error level and then replaced — with two different sizes depending on which code path meets it. The file storer and Block Persister's writer both substitute 128KB (services/utxopersister/filestorer/FileStorer.go:87-92, services/blockpersister/streaming_process_subtree.go:271-275); the two coin-ledger readers substitute 4096 bytes, a 32-fold difference (services/utxopersister/UTXOSet.go:526-531, :568-573). None of the three is the documented 256KB default. So a typo in that one key leaves the node running, writing with one buffer size and reading with another, and the only outward sign is one error line per file handle opened. The key is also present in the shipped file only as a commented line (settings.conf:1621), so the default is what runs, and nothing here has ever exercised the parse failure.

    41. The coin archive is fed by the service that every example switches off¶

    Confirmed, and the dependency runs in the direction that hides it.

    The UTXO Persister's entire input is a pair of per-block files: outputs created, outputs spent (fileformat.FileTypeUtxoAdditions, fileformat.FileTypeUtxoDeletions, pkg/fileformat/header.go:13-14). Grepping services/blockpersister/ for those constants finds nothing, which invites the conclusion that nothing in this repository writes them. That conclusion is wrong, and the reason it is wrong is the finding.

    The writer is utxopersister.NewUTXOSet (services/utxopersister/UTXOSet.go:151-176), called by Block Persister when its own ProcessUTXOFiles switch is on (services/blockpersister/persist_block.go:75-81), which ships enabled (settings.conf:294). The constants live in the imported package, not the caller, so a by-package search separates two halves of one hand-off. Its first log line makes the confusion permanent in the other direction:

    logger.Infof("[BlockPersister] Persisting utxo additions and deletions for block %s", blockHash.String())

    — emitted from the utxopersister package (services/utxopersister/UTXOSet.go:152). Searching the logs by this service's name misses the lines that create its input; searching by [BlockPersister] returns lines written by another service's code. Fourth instance of the mislabelled-door pattern in section 40, and the first one that misleads in the log rather than in a settings file.

    Which sets up the chain that matters operationally. Block Persister is commented out in both Docker overlays (deploy/docker/mainnet/docker-compose.yml, # uses lots of disk space) and blockPersister: enabled: false in both custom resources. utxoPersister: enabled: false in both custom resources, and no container in any compose file. So in every example in this repository the coin archive is off and its feeder is off — coherent. But the dependency means switching on the archive alone does nothing at all: no persister, no ledgers, nothing to consolidate, and per section 42 the service reports that state with the sentence that means caught up. The two switches are three lines apart in the same files and nothing says one requires the other.

    42. "No new block to process" means three different things¶

    Confirmed, and it is the log line an operator will actually see.

    The main loop converts one specific error into a benign-sounding informational message: "No new block to process" (services/utxopersister/Server.go:389-394). Three distinct situations arrive at it, and they want different responses.

    • Genuinely caught up. The bookmark is at or above the processing ceiling, which is reported in its own line one moment earlier (Server.go:468).
    • The ledger for the next block has not been written yet. A missing additions file is a hard error by design — consumeAdditions says so in its own comment, "Unlike deletions, a missing additions file is a …" (services/utxopersister/consolidator.go:265-274) — and the caller turns that error into the idle message. Correct behaviour, wrong noun: the block exists, the block's record does not.
    • A legal block whose deletions ledger will never appear. consumeDeletions deliberately tolerates a missing deletions file, because a block containing only the reward spends nothing, and the comment records the intent (services/utxopersister/consolidator.go:250-262). The tolerance is keyed to errors.ErrBlobNotFound, but the file store signals a missing blob with errors.ErrNotFound, and the error package's Is matches by error code rather than message (errors/Error_types.go:13, :35; errors/errors.go:167-191). The two names never meet, so on the store that ships the tolerance never fires and the block falls through to the same idle message. A block that legitimately spent nothing is then indistinguishable in the log from a block whose records are still on their way.

    The failure mode is not a crash and not a backlog; it is the coin archive stopping while the node looks healthy. The asymmetry is intended and the mismatch of names is not, so this goes to open questions rather than being called a bug.

    Correction after review. The "legal block whose deletions ledger will never appear" does not exist: NewUTXOSet always creates the deletions file with its header, and UTXOSet.Close finalises additions before deletions. A missing deletions ledger means "not written yet" or "half written", never "spent nothing". Tolerating it would roll the block into the set with every spent output still present. The tolerance is removed and the error propagates, which is the stall Server.go documents as the "not written yet" signal.

    43. The archive's lag and the retention that deletes working files are numbers in different repositories — and they apply to different files¶

    Structural, and unmeasured.

    Two constants govern whether the coin archive can catch up after a stall, and neither is in the service that needs both:

    • The processing ceiling is the chain tip minus a hundred blocks, fixed in code (services/utxopersister/Server.go:464, const confirmations = 100 at :46). Not a setting; docs/references/settings/services/utxopersister_settings.md does not list it.
    • The retention window that expires working files is global_blockHeightRetention, 288 blocks (settings.conf:790), the same constant behind Block Persister's two-day fuse (section 36) and the Pruner's default floor (section 14).

    The first version of this note asserted that the coin-difference files carry that retention and was wrong, in a way worth keeping. They do not.

    Block Assembly's height + GlobalBlockHeightRetention arithmetic is real but applies to the subtree pair — FileTypeSubtree and FileTypeSubtreeMeta (services/blockassembly/Server.go:740, and the rewrite path at :886-896) — and Block Persister clears exactly those two when it files (services/blockpersister/streaming_process_subtree.go:85, :91, :231). The additions and deletions ledgers are a different pair: the file storer writes them with whatever options its caller passed (services/utxopersister/filestorer/FileStorer.go:126), the caller passes none (services/utxopersister/UTXOSet.go:155, :160), and the file store's fallback fires only when a retention was configured on the store:

    if dah == 0 && merged.BlockHeightRetention > 0 {   // stores/blob/file/file.go:1105

    That fallback is set by options.WithDefaultBlockHeightRetention (stores/blob/options/Options.go:114-118) — which no non-test code in this repository calls, so for the shipped file store merged.BlockHeightRetention is zero and these ledgers are never scheduled for deletion at all. Confirmed by the read side too: the two places this service opens its own ledgers pass options.WithDeleteAt(0) explicitly (services/utxopersister/UTXOSet.go:510, :553), the convention for "do not schedule anything".

    44. "A checkpoint file for every block" describes the naming, not the behaviour¶

    Documentation divergence, in the UTXO Persister's reference document.

    49. The main-chain cache knows exactly what its own silence means¶

    Structural, and the most careful cache in the services examined so far.

    /merkle_proof and /txmeta need "is this block on the current main chain?", which is owned by the Blockchain service; caching it saves a gRPC round trip per request (services/asset/httpimpl/mainchain_cache.go:37-44). The window size comes from global_blockHeightRetention, defaulting to 288 when absent (:18-22) — the same constant that sets the deletion fuse in sections 36 and 43.

    The design is organised by what absence proves, in three regions (:45-69):

    • Inside the window the set of main-chain block IDs is complete, so it is authoritative in both directions: "present means main chain, absent means NOT main chain. Zero RPC either way."
    • Below the window "missing-means-false does NOT hold", so lookups go to CheckBlockIsInCurrentChain, deduplicated per block ID by singleflight to prevent stampedes on cold IDs, and written back under a generation guard — invalidation increments a counter, and a result fetched before it is dropped rather than stored, which the comment names as closing "the TOCTOU window where a stale result could outlive a reorg".
    • Above the window the block is newer than the set and a rebuild is imminent, so results go straight to RPC, uncached.

    The failure policy is the part worth stealing: if the window has never been populated or a rebuild fails, it is marked unhealthy and every lookup falls back to direct RPC with no caching, and the below-window cache is consulted only while healthy — "healthy window is the precondition for any cached answer", "degraded throughput, never degraded correctness" (:57-72). Below-window entries are cleared on every rebuild and on rebuild failure, for deep-reorg safety (:104-106).

    Rebuilds are serialised on one consume goroutine and pending notifications are drained first, so "a burst of block events coalesces into one rebuild" (:73-77).

    The consequence an operator should know: when this cache degrades, nothing gets wrong. The rest of the node starts paying a round trip per proof request, which shows up as latency elsewhere and as an unexplained load increase on the Blockchain service.

    Confirmed, and the asymmetry is the wrong way round for an operator.

    Before pruning a height the service waits for block assembly to be running and caught up (services/pruner/worker.go:30-70) and separately waits for the block to be marked mined (:72-107).     Confirmed, and it is the sharpest scaling caveat in the service.

    57. sendrawtransaction is a door wearing a window's clothes — and its two storage calls are guarded differently¶

    Confirmed, and it is the reason the RPC surface has to be read as an ingest path, not a query API.

    2. writes it to the blob store — if s.txStore != nil { s.txStore.Set(...) }, :863-871, with the comment "following the pattern from propagation service";
    3. resolves the inputs from the coin store to compute the fee (:899, PreviousOutputsDecorate);

    s.logger.Infof("Max RPC clients exceeded [%d] - disconnecting client %s", ...)
    http.Error(w, "503 Too busy.  Try again later.", http.StatusServiceUnavailable)  // :853
    • The counter is of in-flight requests, incremented and decremented around a single request (Server.go:1353-1359), so "maximum clients" is really "maximum simultaneous requests". The code default is 1 (settings/rpc_settings.go:14); settings.conf:1284 ships 3.
    • No connection survives a response. Every reply sets Connection: close and forces r.Close = true (Server.go:1347-1349), so callers cannot reuse a socket even when the door is idle. There is no Retry-After on the refusal, so the client's only information about when to try again is the phrase "Try again later".
    • No handler ever notices a client giving up. All twenty-nine implemented handlers take the disconnect channel as _ (grep -c "_ <-chan struct{}" services/rpc/handlers.go returns 29, matching the twenty-nine func handle definitions). The channel is populated for hijacked WebSocket connections (Server.go:1209-1216) and the only thing that reads it is handleUnimplemented (Server.go:389-399) — the placeholder. The practical bound on a stuck command is therefore the per-command timeout (Server.go:1015, 30 seconds by default), and a submission whose caller has gone can still spend the coins.

    The design is coherent for an administrative door: shed rather than queue, so a crowd of callers cannot pile up work behind an already-busy Validator. It is the wrong shape for machine traffic, and nothing in the setting's name or description says which of the two it is protecting.

    Confirmed, and the exception is the command an operator reaches for during a reorganisation.

    62. A freeze can report success and freeze nothing, and the failure list cannot tell you¶

    Confirmed from the code's own comment, and the reporting shape makes it invisible.

    AddToConsensusBlacklist derives the coin identity it hands to the store from the transaction record on this node (services/alert/node.go:296, :325-326). The comment at :319-324 states the hazard outright:

    The two agree only while the stored transaction is byte-faithful. A node bootstrapped from a UTXO-set snapshot stores input-less reconstructions that retain no inputs, version or locktime, so they hash to something else entirely; the UTXO hash derived from them matches nothing in the store, and the freeze then reports success while blacklisting nothing.

    The response type cannot distinguish the outcomes. Every failure branch appends the coin and a reason to response.NotProcessed — bad txid (:291), missing parent (:298), nil output (:313), hash derivation failure (:329), store error (:342, :347) — and the success path appends nothing (:339-351). So a run that froze five coins and a run that matched zero both return an empty failure list, and neither the caller nor the alert network can tell them apart.

    The consequence runs into the next command in the protocol. Reassignment requires the coin to be frozen: the SQLite store raises "transaction %s:%d is not frozen" when the flag is clear (stores/utxo/sql/alert_system.go:167-169). So on a snapshot-seeded node the freeze silently matches nothing, and the confiscation that follows fails loudly with an error naming the freeze — pointing the investigation at the alert service rather than at how the node was seeded.

    Worth pairing with the seeding discussion this file has carried since section 9: the trade-offs of snapshot seeding are documented in terms of disk and cost, and nowhere in terms of the alert service answering instructions differently on a seeded node than on a synced one.

    63. Confiscation rewrites the commitment to a locking script it never stores¶

    Confirmed in both store implementations, and named in the code as issue 1725.

    The alert path builds the new world and hands it over (services/alert/node.go:456-495): a public key is extracted from the confiscation transaction's unlocking script, a P2PKH locking script is built from it, an amended output is assembled with the original satoshi amount, and a new UTXO hash is derived that commits to that script. Then:

    Calculate the replacement commitment. ReAssignUTXO does not persist the replacement script, so changing the owner currently strands the output for both owners after mandatory re-extension (issue 1725).

    Both stores confirm it. SQLite updates three columns and nothing else — utxo_hash, frozen, spendableIn (stores/utxo/sql/alert_system.go:181-188) — so the stored locking script is still the original one while the stored hash now commits to a script that exists only in the alert. Aerospike dispatches a Lua routine with the old hash, the new hash, a height and a delay (stores/utxo/aerospike/alert_system.go:244-251); no script is among its arguments, so it cannot store one either.

    Operationally that means the previous owner cannot prove the coin, because the commitment moved, and the new owner cannot spend it, because the script never arrived — and the coin is held for a thousand blocks on top (stores/utxo/Interface.go:49), so the stranding outlasts most incident windows. The design is sound; the write is one column short. Recorded because the note that explains it is a comment inside a loop body, and the effect is that an emergency instruction leaves a coin unusable by anyone.

    69. The file-handle budget is tuned for a limit no Teranode container sets¶

    Confirmed, and the design choice is deliberate and well-argued; the gap is in the examples.

    The file store meters open files with two process-global weighted semaphores — reads and writes separately, because one shared counter deadlocked (stores/blob/file/file.go:328-339) — with defaults of 768 and 256 (settings/block_settings.go:25-27). settings.conf explains the arithmetic and then hands the operator the job:

    These limits protect against Linux ulimit exhaustion by controlling concurrent file descriptors. Total: read + write should stay under your system's open file limit (ulimit -n), leaving room … The limit itself is the operator's to set (ulimit -Hn, systemd LimitNOFILE, container --ulimit)

    — settings.conf:504-511

    Both knobs are then commented out, so the defaults stand (settings.conf:516-517).

    What the code does when the limit is smaller than the budget is a considered choice, written at the point of use:

    The semaphores bound how many file operations run at once, but they cannot bound what the OS allows, so fit them under the descriptors it actually leaves us rather than refusing to start (issue 1431).

    Clamping, not refusing, is the important choice.

    — stores/blob/file/file.go:438-442

    That is the right shape of decision, and it is why nothing breaks. The gap is that the examples never set the limit for the services that need it. In the Docker catalogue exactly one container declares ulimits, and it is a database:

        ulimits:
      nofile:
        soft: 15000
        hard: 15000

    (deploy/docker/base/docker-services.yml:193-196, inside the aerospike-tn block.) No Teranode service block sets it, and grep -rn "ulimit\|nofile" deploy/kubernetes/ returns nothing at all — the Kubernetes examples carry no ulimit, no securityContext.sysctls and no annotation mentioning the open-file limit.

    So the number in force is whatever the container runtime hands out, and on a common default of 1024 the clamp reduces both counters at start-up and says so once, at INFO, naming both numbers (stores/blob/file/file.go:1759-1781). Nothing is wrong; the node simply runs with a smaller read path than the settings text advertises, and the only evidence is a line most operators never read at INFO level. Two consequences worth stating plainly:

    • commissioning should include one command per service — docker exec <service> sh -c 'ulimit -n' — and the answer belongs next to the throughput expectations the same files set;
    • the budget is per process, so this is section 56's arithmetic with file handles instead of database connections: N replicas of a blob-touching service ask for N times the descriptors, against a limit nothing in these files raises.

    70. The address of a coin in the ledger includes a number that the shipped contexts disagree about¶

    Confirmed from the code's own warning and three values in one file.

    With the Aerospike engine, a transaction's outputs are stored in chunks, and which chunk holds an output is computed from the output index modulo a configured size:

    return vout % uint32(s.utxoBatchSize)

    (stores/utxo/aerospike/aerospike.go:920; the read path does the same arithmetic at stores/utxo/aerospike/get.go:356, and chunk construction at stores/utxo/aerospike/create.go:664-671.) The size comes from settings:

utxostore_utxoBatchSize.docker   = 50

    (settings.conf:1731-1733.) Because the value is part of how a location is computed, it is not a tuning knob — it is part of the address of every coin already on the disk, and the constructor says as much, without hedging:

    // It's very dangerous to change this number after a node has been running for a while

    Limits of the claim, stated plainly. Only the Aerospike engine shards this way; the SQL engine keeps the outputs in a row. And the two shipped contexts that differ are not both pointed at one data directory in these files — utxostore.docker.ss.teranode1 is a PostgreSQL address outright (settings.conf:1630). So this is a hazard documented in the code and left unenforced, not a fault observable in the shipped stack.

    71. The ledger's own files are deliberately outside the delete-at-height promise, and the setting that appears to govern them does not¶

    Confirmed at the point of construction, with the reason written down.

    The deletion arrangement this file has described repeatedly — the Blockchain service holds a promise, the Pruner fulfils it, and a file carries the height at which it may go (§51) — does not apply to the files the UTXO store writes. The store turns the mechanism off while building its blob store:

    // Create external store with DAH explicitly disabled
// External file lifecycle is managed by the Aerospike pruner service, not by DAH files

    (stores/utxo/aerospike/aerospike.go:337-338, passing options.WithDisableDAH(true); individual writes also pass options.WithDeleteAt(0) at stores/utxo/aerospike/create.go:1157.)

    The reason is sound: the rule for these files is "delete a fully spent parent once every spending child is mined and comfortably old" (docs/utxo-safe-deletion.md), and a height on a file cannot express "once every child is verified". So the store keeps its own clock, unminedSince, and handles the reorganisation case by stamping a transaction that has fallen back to pending with a timestamp from the past, so it does not win a fresh full grace period by being re-org'd (stores/utxo/pruner_unmined.go:16-35, stores/utxo/aerospike/longest_chain.go:77, both citing issue 1768).

    The consequence for operators is the part worth recording: the two numbers that decide when the ledger forgets appear nowhere in settings.conf. utxostore_unminedTxRetention and utxostore_parentPreservationBlocks have zero occurrences in the file — grep -c on each returns 0 — and both are computed at load time from constants belonging to other concerns:

    UnminedTxRetention:        getUint32("utxostore_unminedTxRetention", globalBlockHeightRetention/2, alternativeContext...),
ParentPreservationBlocks:  getUint32("utxostore_parentPreservationBlocks", blocksInADayOnAverage*10, alternativeContext...),

    (settings/settings.go:505-506, with blocksInADayOnAverage = 144 at settings/settings.go:31.) Since global_blockHeightRetention = 288 in the shipped file (settings.conf:790), the ledger's unmined grace period is 144 blocks, derived by halving a number that lives in another service's section of the configuration. An operator who lowers global_blockHeightRetention to buy back disk space halves the ledger's grace period as a side effect, silently, and will find no hint of the coupling in the file they edited — which is another instance of the pattern section 32 named, and the first where the derived value is a deletion deadline rather than a timeout.

    74. Two partition counts, and the default context has them eight apart¶

    The v2 routing divides by validator_txmeta_numPartitions, which defaults to 32 (settings/settings.go:488, absent from settings.conf). The topic's own partition count comes from a different variable in a different file: kafka_txmetaConfig builds its URL with partitions=${KAFKA_PARTITIONS_HIGH} (settings.conf:853), and that is 8 in the shared default context, 32 only in docker.m and operator (settings.conf:38-40).

Two numbers that must agree, nothing comparing them, and the safe thing about the situation is only that v2 is off by default. The same settings file raises the topic to 32 for the two deployment contexts that would need it (settings.conf:39-40) without touching the producer's number, so the pairing works by coincidence in those contexts and fails in the one an operator would use for a laptop run.

    76. Eight of fourteen services publish a contract, and two of those call it something else¶

    Structural finding, affects any survey done by filename.

    The convention says a service publishes its surface in a file named Interface.go, with a matching Client.go holding the wire handling. Measured across services/:

    • Eight services have a contract file: Block Assembly, Blockchain, Block Validation, Legacy (as peer/Interface.go), P2P, Propagation, Subtree Validation, Validator.
    • Six have none: Alert, Asset Server, Block Persister, Pruner, RPC, UTXO Persister.
    • Eight have a Client.go, the same eight.

    Two of the eight deliberately misname it. Propagation's is ClientInterface.go (services/propagation/ClientInterface.go:20) and Block Assembly's contract is called ClientI (services/blockassembly/Interface.go:66) with a second contract Store below it (:232). A filename survey for the convention therefore finds six of eight and reports the wrong denominator. The guide's interfaces table is built by reading files rather than by listing names.

    Of the six without one, three are pure wire services — Alert, Asset Server and Pruner each expose a gRPC contract with no in-process caller in this repository — which is a coherent position. The other three are not: Block Persister consumes Kafka and writes files with no published surface of any kind, RPC is reached only over HTTP, and UTXO Persister is reached only over Kafka. For those three, "what may I ask this service" has no answer in Go.

    77. The no-protobuf rule broke on the bus, not on a door¶

    Convention violation, and the one that costs something.

    The convention forbids protobuf types in a published interface, and the reference implementation named alongside it is P2P. Measured, compliance is close to total where the surface is small and absent where it matters:

    Service Published questions Accepting a wire type
    P2P 26 0
    Validator 6 0
    Block Validation 6 0
    Subtree Validation 3 0
    Propagation 1 0
    Block Assembly 18 3
    Blockchain 73 5
    Legacy 6 6

    The P2P reference is clean, which is worth stating because it is the existence proof that the rule is workable at this surface size.

    The violation that matters is not a count but a type. Blockchain's event bus takes and hands out a protobuf structure — SendNotification(ctx, notification *blockchain_api.Notification) (services/blockchain/Interface.go:111) and Subscribe(ctx, source) (chan *blockchain_api.Notification, error) (services/blockchain/Interface.go:558) — and every service in the node subscribes to that channel. So the wire type the rule was written to keep out of the interior is now the parameter type of the most widely used interface in the system, and the conversion the rule wanted in one place lives instead in every consumer. blockchain.FSMStateType is the workaround: a hand-written wrapper over the enum (services/blockchain/Interface.go:72), which is evidence the leak was noticed and managed rather than closed.

    78. Six of nine gRPC doors accept any caller, and the settings file says so twice¶

    Security posture, arguable but deliberate.

    One shared credential, grpc_admin_api_key, is the only interior authentication in the system. Of the nine services that start a gRPC server, three install an interceptor that checks it — Blockchain (services/blockchain/auth.go:12-19, with a public-method exception list), Legacy (services/legacy/Server.go:787-804) and P2P (services/p2p/Server.go:1389).

    The other six start their servers with nothing to check. That is verified by the last argument to each StartGRPCServer call, which is the auth options: nil for Validator (services/validator/Server.go:483), Block Assembly (services/blockassembly/Server.go:1081), Block Validation (services/blockvalidation/Server.go:1233), Subtree Validation (services/subtreevalidation/Server.go:589) and Pruner (services/pruner/server.go:301). Propagation builds an auth options block and fills in only a ban-list hook (services/propagation/Server.go:355-361), and the shared server helper installs an interceptor only if RequireAuthByDefault is set or an API key is present (util/grpc.go:83-88) — neither is true there, so Propagation's door is open as well.

    Nothing encrypts any of it. security_level_grpc = 0 (settings.conf:1310) with no context override, so no certificate is read at all (util/grpc.go:62-71 skips the cert loading when the level is zero, which is also why the shared credential declares it does not need transport security, util/grpc_helper.go:66-68). The settings file documents both halves of this plainly — the shared key paragraph explains that only the Blockchain's health endpoints are public (settings.conf:800-808) — but nothing in it states that the remaining six doors have no check at all, which is the sentence an operator would need.

    79. The credential every service needs is defined nowhere in the repository¶

    Deployment gap, one-line fix.

    Blockchain treats the credential as a condition of existing: ValidateRequiredAdminAPIKey rejects an empty value, one with padding, a well-known placeholder, or anything under sixteen characters (util/grpc_required_auth.go:17-22, util/admin_api_key.go:29), and it is called before the Blockchain starts its listeners (services/blockchain/Server.go:524-525). Its clients check the key against the live door before accepting the connection and give up if it is refused (services/blockchain/Client.go:158-163).

    The requirement is documented: the development cluster file says "REQUIRED: include grpc_admin_api_key for Blockchain startup and all service clients" (deploy/kubernetes/teranode/teranode-cr.yaml:82-83) and points at a secret named teranode-operator-secrets (:85-86). But no kind: Secret exists anywhere under deploy/, and the key has no value in settings.conf — only the comment describing it (settings.conf:800-808).

    So a node started from this repository's own manifests cannot start: Blockchain exits, and its clients exit behind it, because the one setting all of them share has to be created outside the tree. That is defensible for a secret and normal practice — but the mainnet cluster file states the same requirement in a comment (deploy/kubernetes/teranode/teranode-cr-mainnet.yaml:93) while the docker examples carry no mention of it at all, and a reader who starts from Docker will get an unhelpful failure first.

    80. The resolver written for Kubernetes is registered and then overwritten¶

    Dead-as-shipped code, provable from two files.

    pkg/k8sresolver is a resolver written for this project specifically — four hundred and sixty-seven lines outside its tests, a thousand one hundred and eighty-four with them. It builds in-cluster credentials (pkg/k8sresolver/k8s.go:30-41), lists and watches the cluster's endpoint records for a namespace (:66, :100-104), and caches the answers with a per-name key (:53-61). Its builder registers the scheme k8s (pkg/k8sresolver/builder.go:69-71).

    It is installed in util/grpc_helper.go:525-537, in a switch on the resolver setting:

    case "k8s":
    resolver.Register(k8sresolver.NewBuilder(logger))
    resolver.SetDefaultScheme("k8s")
case "kubernetes":
    resolver.Register(k8sresolver.NewBuilder(logger))
    kuberesolver.RegisterInClusterWithSchema("k8s")

    The kubernetes branch registers two builders under the same scheme name, and gRPC's registry is a map assignment keyed by scheme (google.golang.org/grpc@v1.82.1/resolver/resolver.go:54-56, m[b.Scheme()] = b), so the second call replaces the first. The shipped production context selects kubernetes (settings.conf:815), which means the in-repo resolver is constructed, registered, and discarded on every start. The branch that would keep it — k8s — is selected by nothing: no line in settings.conf and nothing under deploy/ sets that value.

    Two consequences are worth knowing. The in-repo resolver's own logging and caching are not what production runs on, so behaviour questions about service discovery should be answered from the upstream package, not this one. And the lookup watches endpoint records (pkg/k8sresolver/k8s.go:66), a permission no manifest grants — not because a manifest grants the wrong thing, but because the repository contains no Role, ClusterRole, RoleBinding or ServiceAccount object at all. Across deploy/kubernetes/ the kinds present are Service, ConfigMap, StatefulSet, PersistentVolume, PersistentVolumeClaim, NetworkPolicy, Deployment and Cray Cluster; a case-insensitive sweep of every manifest in the tree finds no RBAC kind anywhere. The single place the word appears is Aerospike's StatefulSet, which uses it to turn the mounted token off (deploy/kubernetes/aerospike/aerospike-statefulset.yaml:20, automountServiceAccountToken: false) — the opposite of what a resolver needs, and in a different product's pod. Teranode's pods therefore run under the namespace's default service account. That permission gap applies to whichever resolver runs, because the upstream in-cluster resolver needs the same access.

    Whether it bites depends on facts outside this repository. A cluster may grant discovery read access to default by policy, or an operator may apply RBAC when installing the operator itself. The repository can only say the grant is absent from its own manifests, which is what this finding claims and nothing more. It can also say the Docker smoke path would never notice: there the resolver setting is dns and this code is not reached.

    81. The busiest interface in the design is switched off by a default¶

    Config finding, changes the meaning of every client table.

    useLocalValidator = true (settings.conf:1602). The key carries no context suffix, so it is true in every context including operator.

    Its effect is in the one function every service uses to reach a Validator: when the flag is set, the process builds a Validator inside itself instead of dialling one (daemon/daemon_stores.go:280-283), constructing its own UTXO store and its own Block Assembly client while it does. Four services ask for that client — RPC (daemon/daemon_services.go:567), Block Validation (:820), Propagation (:1085) and Legacy (:1164) — and in the shipped configuration, not one of them opens a connection to the Validator service.

    The Validator's gRPC door is still built, and its five published methods still exist, but nothing in this repository dials them except the diagnostic commands (cmd/monitor/monitor.go:200, cmd/diagnose/health_checks.go:139). The service is reached over the conveyor belt instead, and the eight replicas in the production-shaped example (deploy/kubernetes/teranode/teranode-cr-mainnet.yaml:183) do block and transaction work arriving on Kafka, split by partition rather than by client-side spreading — which is the reason the topic that carries that work is given thirty-two partitions in the same file (settings.conf:859).

    The address it would dial is also wrong for a split deployment: validator_grpcAddress is 0.0.0.0:${VALIDATOR_GRPC_PORT} (settings.conf:1743), a listen wildcard sitting in a dial slot, where every other service's dial target is a name to look up. On Linux, dialling 0.0.0.0 means "this machine", so clearing the flag without correcting that line makes each copy of the Validator call itself.

    82. The fast lane has no sender, and its default interface belongs to a Mac¶

    Interface surface, dormant twice over.

    Propagation can listen for transactions on IPv6 multicast (services/propagation/Server.go:435-476) and the settings file documents the address as a comment (settings.conf:828-830). Every deployment in this repository leaves it unset, which is the first reason it is dark. It is also receive-only, which is the second and less visible one.

    The listener reads and nothing else: ReadMsgUDP at services/propagation/Server.go:499, with the socket list otherwise used only to append (:474-476) and to close (:603-609). A search of the whole tree for a UDP write finds one file, services/legacy/upnp.go, which is talking to a router. So a transaction arriving by multicast can be heard and cannot be answered in kind — it leaves by the ordinary gRPC and Kafka routes, which means the lane is an ingest path and not a propagation path, whatever the service is named after.

    Two defaults would catch an operator who switched it on. The interface falls back to en0 (services/propagation/Server.go:439-441), which is the macOS device name; a Linux host gets a clean startup failure instead of a guess (:445-446). And an empty source allowlist is read as accept-everything, logged as such (:456-458) — with no credential involved, since the key check in util/grpc.go:83-88 is not on this path at all.

    83. The ledger store was written for a second instance, and the settings file hides the ceiling¶

    Design evidence, plus a shipped-default trap.

    stores/blockchain/sql is the only component in this tree whose comments describe more than one Blockchain process running against one database, and describe it in the past tense of something that happened.

    The design evidence is the durable reservation table. A block needs a number before it commits, and two paths can bring the same block in during initial sync — Legacy netsync and Block Validation catch-up. Without a shared authority "each calls nextval and gets a DIFFERENT id, one of which is written into the block's UTXO mined-info while the block commits under the other — orphaning the first id (a phantom that later fails checkOldBlockIDs and wedges sync)" (stores/blockchain/sql/sql.go:128-136). The guard has two levels: an in-process cache behind a mutex, and a table whose entries "survive ttlcache TTL expiry, restart, and a second instance" (stores/blockchain/sql/assign_block_id.go:62-63), inserted with ON CONFLICT so a second process cannot claim a promised number (:108). The mutex is explicitly documented as covering only this process, with cross-process races left to the table (:43-44).

    The incident evidence is stronger. Schema creation at startup is serialised behind a fixed advisory lock whose constant carries the comment "must be unique per schema-creation context and stable across releases" (stores/blockchain/sql/sql.go:477-479) — a number two processes have to agree on. And the fast path exists because of a specific cascade, described in the code: every DDL statement takes a SHARE lock on blocks; a concurrent instance's on_main_chain rebuild holds ROW EXCLUSIVE on the same table for the length of the walk; shared requests queue; Postgres queues fairly, so ordinary SELECTs arriving afterwards line up behind the queued DDL. "That cascade is what blocks readers during otherwise idle startup" (stores/blockchain/sql/sql.go:484-493). The fix probes the catalog, which locks no table in the ledger (:494-500).

    None of that is reachable with one instance. So the store is designed, and has been field-tested, against a topology no deployment in this repository runs.

    The shipped-default trap is separate and smaller. util.InitSQLiteDB ignores every pool setting and fixes the connection ceiling at five, with a comment naming the cause: the driver's working memory lives in a global arena that never returns pages, which drove "sql.test's bimodal 2G/34G swing and the intermittent OOM (#1051)" (util/sql.go:283-290). Defensible — SQLite serialises writes anyway. But the default ledger store is the file engine (settings.conf:483), and the same file offers postgres_maxOpenConns = 50 (settings.conf:116) with a per-service override documented but commented out (:130). So the shipped default runs five database operations at a time, and the settings file contains two numbers that suggest otherwise.

    84. The chain-walk cache is stale on purpose, and the freshness setting is off¶

    Two switches that only make sense together, one of them off.

    The store caches the results of parent-walking queries for ten minutes (chainWalkCacheTTL, stores/blockchain/sql/sql.go:53), and clears it on exactly four events — store-time reorg detection, invalidation, deletion, revalidation (stores/blockchain/sql/StoreBlock.go:357, InvalidateBlock.go:139, DeleteBlock.go:79, RevalidateBlock.go:56) — and explicitly not when a block is written or a block field updated (stores/blockchain/sql/sql.go:1314-1318). The reasoning is sound and stated: parent links never change, so only a change of on-chain status can make a cached walk wrong.

    The other switch decides whether the walk happens in memory or in SQL: blockchain_use_in_memory_chain_check (settings/blockchain_settings.go:26), and the shipped value is false (settings.conf:466). So as configured, every membership question goes to the database, in batches of a thousand because Postgres refuses roughly thirty-two thousand bind parameters (stores/blockchain/sql/CheckBlockIsInCurrentChain.go:13-17), on an engine whose concurrency ceiling is five by default (section 83). The two settings are individually reasonable and jointly a tuning conversation nobody appears to have had: the cache that would make the SQL path cheap is the one the setting switches off.

    Worth an operator's attention rather than a code change, and worth measuring before concluding — neither number is visible in the shipped metrics without looking at the database.
