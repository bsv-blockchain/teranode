The PostgreSQL UTXO Store

A plain-English tour of how Teranode keeps the set of spendable coins in PostgreSQL — and the unusual “deferred delete” trick at its heart.

Who is this for? Anyone — you do not need to know Bitcoin internals or PostgreSQL. We build up from zero. If you only read one section, read “The clever bit: deferred deletion.”

1. What this thing is

A Bitcoin (BSV) node has to remember which coins currently exist and can be spent. That set is called the UTXO set. Every incoming transaction must be checked against it — fast, and millions of times — and the set is constantly changing as coins are spent and created.

This package is one place to store that UTXO set: a storage backend built on a normal PostgreSQL database, using the Go library pgx. Teranode can use different backends (Aerospike, SQLite, this one) — they all implement the same Go interface (utxo.Store), so the rest of the node doesn’t care which one is plugged in.

Two goals shape every decision here: (1) be fast under heavy concurrent load (tens of thousands of transactions per second), and (2) never lose data — these are real coins, so everything is written durably to disk (synchronous_commit = on).

2. UTXOs in 60 seconds

A transaction has inputs (coins it spends) and outputs (new coins it creates). Each output is a coin. A coin that hasn’t been spent yet is an Unspent Transaction Output — a UTXO. When a later transaction uses that coin as an input, the coin becomes spent and is no longer part of the live set.

So the store really only needs to answer a few questions, very quickly:

  • Does this coin exist, and is it still unspent? (validate an input)
  • Mark this coin as spent. (apply a transaction)
  • Store the new coins this transaction creates.
  • Eventually, throw away coins that are long gone so the database doesn’t grow forever.

That last one — “eventually throw away” — is where the interesting design lives.

3. The big idea: two tables

Many designs use a separate row for every single output. This store does not. It uses just two data tables — plus a few small bookkeeping tables (described after the diagram):

Why fold the outputs into the transaction row instead of a separate “outputs” table?
A typical transaction has only a handful of outputs. Storing them as a separate row each means millions of extra tiny rows and an extra random-access index to maintain on every write. By packing a transaction’s outputs into the transaction’s own row, validating a spend reads one row — no joins, no second index. The trade-off: this is tuned for ordinary transactions; transactions with enormous numbers of outputs are a known weak spot.
(The full “why not normalise into many tables like the SQL store?” story is in §11.)
The small bookkeeping tables. Besides txs and spends, a few tiny tables keep the background machinery honest. None sit on the hot validation path, and all are negligible in size:
  • dah_part_watermark — the deferred-deletion sweeper’s “bookmark”: how far each shard’s sweep has progressed (one row per shard; see §7). This is the bookmark referred to under crash-safety in §9. dah_sweep_control next to it holds the kill switch and tuning knobs, so operations can adjust the sweeper with a plain SQL update.
  • pending_deletes — the pruner’s to-do list: (transaction, delete-at-height) pairs written the moment a sticky note is stamped, and removed by whoever clears a note. The pruner reads only this list — it never scans the big tables looking for work.
  • pending_unmined — a small “not mined yet” listing kept up to date by a background writer (with a filter so transactions that mine within a second or two never touch it at all), used by cleanup jobs that expire long-unmined transactions.
  • dah_dirty_parents — a tiny “please re-check these” queue: when a reorg un-spends a coin, the affected parent transactions are queued here in the same database transaction, and the safety-net worker re-derives their state from the ground truth soon after (see §9).
  • conflict_intents — a small write-ahead log for conflicting-transaction handling (marking a transaction conflicting, and reversing that during a reorg). An intent row is written before the work begins and deleted when it completes, so a crash mid-operation is replayed cleanly on restart instead of leaving a conflict half-applied.
The “two tables” framing is about where the UTXO data — and every hot-path read and write — actually lives; these auxiliary tables are rarely touched and exist only to make the background workers crash-safe.

5. The spends table — one row per spent output

This table records the act of spending. There is no “is spent” flag anywhere — instead:

👉 A row existing in spends is the fact that the coin is spent. No row = unspent. Row present = spent.
ColumnPlain meaning
prev_tx_hashThe transaction that created the coin being spent.
prev_output_idxWhich output of it (output #0, #1, …).
spending_dataWho spent it: the spending transaction’s ID + which input.
spent_at_heightThe block height at which it was spent. (Remember this — it matters for deletion.)
The double-spend guard is the table’s own uniqueness rule. There is a UNIQUE (prev_tx_hash, prev_output_idx) constraint. So the very first attempt to spend a given coin inserts a row and succeeds; a second attempt to spend the same coin fails the insert — the database itself refuses it, and we read back the existing row to report who already spent it. No locks, no read-then-write race: the unique index is the referee.
Why a separate table for spends, instead of a flag on the output? Inserting a new row is cheap and append-only. Flipping a flag on the transaction row would rewrite that row on every spend, creating churn the database then has to clean up. Keeping spends as pure inserts keeps the busy “spend” path lean.

6. What happens during a spend

When a new transaction spends a coin, the store does this (simplified):

1
Look up the parent transaction’s row by its hash — one read. Everything needed (the output’s ID, whether it’s spendable/frozen, coinbase maturity, whether the parent is locked/conflicting) is right there in that single row.
2
Check the rules: the output ID must match, it must not be frozen/locked/conflicting, coinbase money must be mature, etc.
3
If all good, insert a row into spends recording the spend and the height. The unique constraint guarantees it can’t be double-spent.
4
That’s it. The store does not stop to figure out whether the parent is now fully spent and ready for deletion. That decision is deferred. ↓ (see §7)

7. The clever bit: deferred deletion ★

The problem. A coin can be deleted once its transaction is fully spent, buried deep enough that it won’t be reorganised away, and no longer needed. But checking “is this whole transaction fully spent now?” on every single spend is expensive — you’d have to count this transaction’s spends, compare to its spendable outputs, and write the answer back onto the busy transaction row. Doing that on the hot path would drag throughput down.

The solution, in one sentence: the busy path just scribbles down heights; a calm background worker reads those scribbles later and decides when each transaction may die.

Think of a restaurant:

🍽️ Waiters (the hot path) take orders as fast as they can. They don’t stop to figure out which tables are finished — they just note “this dish was served at 7:42.”
🧹 A busser (the background worker) strolls the floor, sees which tables are actually done, and puts a little “clear after 9 pm” sticky note on them.
🗑️ The cleaner (the pruner) comes by and simply clears every table whose sticky-note time has passed. The cleaner doesn’t think — it trusts the note.

The three moving parts

What the sweeper actually does: fold, don’t recount

The sweeper walks the new spends rows in height order, and for each one flips the matching bit in the parent transaction’s spent_bits bitmap. That’s the whole trick: the answer to “is this transaction fully spent?” is carried forward on the transaction’s own row, one cheap bit at a time, instead of being re-derived by re-reading its whole spend history. Earlier versions of this store re-counted a transaction’s spend rows at stamping time — for an old transaction spent over years, those rows are scattered across cold disk, and that re-reading is exactly what fell behind on real networks. It is gone: no stage of stamping ever re-reads spend history.

Flipping a bit twice is harmless (it’s already set) — so if a reorg forces the sweeper to re-process a height range, nothing drifts and nothing double-counts. That one property (idempotence) is what makes the whole scheme safe to re-run at any time.

For a transaction to get a delete_at_height sticky note, all of these must be true:

  • It’s mined (it’s in at least one block).
  • It’s on the main chain (unmined_since is empty).
  • It’s fully spent — every spendable output’s bit is set (bit_count(spent_bits) = spendable_count) — a single-row check.
  • It isn’t preserved (preserve_until is empty).

If so, the note is set to:

delete_at_height = completion_height + 1 + retention
where completion_height = the latest of (its spends’ heights, its mined height), and retention is a safety buffer of blocks (so we keep things around well past the point of any realistic chain reorganisation). If a transaction stops qualifying, the sweeper clears the note again.

How the sweeper finds work without scanning everything

Spend rows are written in roughly increasing height order, and an index on (spent_at_height, …) lets the sweeper read them back in exactly that order. It works in bands sized by row count (200,000 spends at a time by default), not by height: a band is a fixed amount of work whether the chain is sparse or one block carries millions of spends — a single dense block is simply drained as one band of its own. Each band’s sorting memory is pinned so the work never spills to temporary files, and each band commits atomically (fold + stamp + bookmark advance in one transaction), so an interruption costs at most one band.

A safety net underneath: a “reconciler” loop re-derives spent_bits from the actual spends rows for a bounded slice of transactions at a time — and it drains the dah_dirty_parents queue first, so anything a reorg touched is re-checked within seconds rather than whenever the slow rotation happens to arrive. It normally finds nothing — it exists so that “we’ll get to it eventually” is a guarantee, not a hope.
Why is this unusual / worth calling out? Most stores decide “delete-ability” at the moment a coin is spent (synchronously). This store deliberately splits that into a cheap “write down the height” step on the hot path and a separate, batched, rate-controlled “decide & stamp” step in the background. The result is that the validator’s spend path stays a lean append, while the expensive bookkeeping happens off to the side — and the final deletion is a trivial range delete.

8. The three workers, summarised

HOT PATH

Validator operations

Create, Spend, mark-as-mined, lock/unlock. Runs constantly, batched for speed. Only ever tags heights; never computes delete-ability.
BACKGROUND

The DAH sweeper (“Worker 2”)

One loop per shard: folds each new spend into the parent’s spent_bits bitmap in row-bounded bands, stamps delete_at_height the moment a mined transaction’s bitmap is full, feeds pending_deletes, and advances its bookmark — all in one atomic step per band. Plus the reconciler safety net.
BACKGROUND

The pruner

Reads its to-do list (pending_deletes) and deletes every transaction whose delete_at_height has arrived, removing its spends rows alongside it, in bounded set-based batches, all shards in parallel. Intentionally simple so it’s fast.
DESIGN

The contract between them

The pruner trusts the sticky note. So the responsibility for “only set the note when it’s truly safe” lives with the sweeper and the height-tagging steps — not the pruner.

9. Staying correct: reorgs and crashes

Two things could threaten the “sticky note” being right:

Chain reorganisations (a block gets undone)

If history changes, a transaction that looked finished might become un-spent or fall off the main chain. The store handles this:

  • Un-spend removes the spends rows, clears exactly those bits in the parent’s spent_bits, clears delete_at_height, removes the parent from pending_deletes — and queues the parent in dah_dirty_parents, all in one database transaction, so the safety net re-verifies it from ground truth within seconds.
  • Falling off the main chain sets unmined_since and clears delete_at_height (and the pending_deletes entry) — a transaction that’s no longer on the main chain must not be pruned at its old note.
  • Rewinding the bookmark: after a reorg the watermark is moved back so the affected height range gets swept again with fresh facts. Because folding is idempotent (setting a set bit changes nothing), re-sweeping the surviving history is completely harmless — this used to be a genuine drift hazard in the counter-based design, and the bitmap removed it by construction. The sweeper’s bookmark advance is also a compare-and-swap, so a rewind that lands mid-band makes the band roll back and re-run rather than being silently overwritten.
This is the key rule that keeps the “dumb, fast pruner” safe: whenever a transaction stops being eligible, the setters clear its note. The pruner never has to second-guess.

Crashes

  • All tables are durable (LOGGED) and commits are synchronous, so a crash never loses confirmed data.
  • The sweeper’s bookmark is itself stored in the database, so after a restart it picks up exactly where it left off. Re-doing a little work is harmless because stamping the same note twice changes nothing.

10. Partitioning & speed

Both txs and spends are split into 8 shards (“hash partitions”) on the transaction hash, using the same rule for both. That means a transaction and its spend records always live in the matching shard pair (txs_p03 ↔ spends_p03). Benefits:

  • Parallel cleanup: the sweeper and pruner can work shard-by-shard at the same time, and deleting a transaction and its spends touches only one shard pair — no cross-shard contention.
  • Vacuum keeps up: PostgreSQL’s background tidying runs per shard, so it doesn’t fall behind on one giant table.

Other speed/robustness choices:

  • Batching: creates, spends, reads and unlocks are grouped and sent to the database in bulk (fewer round-trips, bigger set-based queries).
  • One-row reads: validating a spend reads a single row (thanks to the folded outputs).
  • Append-only spends: spending never rewrites the transaction row.
  • Shard-exact lookups: batch statements address the sharded tables through a join that lets PostgreSQL route each hash to exactly its own shard’s index — the naive form probed all 8 shard indexes per lookup (measured: ~5 index descents per row where 1 suffices).
  • No index on anything the background writers update: the fold/stamp columns are deliberately unindexed so those updates stay cheap in-page operations (an index there measurably collapsed update performance).
The one-line mental model: two tables (transactions + spends), outputs folded into the transaction row, spending is a cheap insert guarded by a unique index, and deletion is deferred — tag heights now, let a background worker decide the “delete after” height, then delete trivially.

11. Why so few tables? (the performance story)

If you’ve done database design before, the two-table layout probably looks wrong. The textbook approach — and what Teranode’s older SQL UTXO store does — is to normalise: a table for transactions, a table for outputs, a table for inputs, a table for block links, tied together with foreign keys. That’s great for general-purpose databases. Here it’s the slow path. This section explains why.

The core insight: this store has exactly one demanding job — validate spends and reclaim old coins, at tens of thousands of transactions per second, written durably to disk. At that speed the thing that hurts most is how many random disk writes each transaction causes. Every extra table, every extra index, and every “update a row in place” turns into more random writes. So the design works backwards from that: do the fewest writes possible per transaction.

What a normalised design costs at high speed

In a fully normalised schema, a single transaction with, say, 3 outputs and 2 inputs becomes many rows across several tables (1 transaction + 3 outputs + 2 inputs + block links). Multiply by tens of thousands of transactions per second and you get:

  • Row explosion → write amplification. Each of those rows is inserted into a table whose index lives in a different place on disk, scattering the writes. The single biggest cost in this workload is exactly this: random-position index inserts. More rows per transaction = proportionally more random writes.
  • Every index is a tax on every write. A separate outputs table needs its own big index keyed on a (random) hash — a second scattered B-tree to maintain on every insert. The SQL store also keeps a special “is this output still unspent?” index that gets disturbed on every spend — a known cause of multi-second disk stalls under load.
  • “Mark as spent” rewrites a row. The normalised way to spend a coin is to update the output row (fill in who spent it). Updating a row leaves a dead copy behind that the database must later vacuum, and it disturbs that unspent-index. That’s churn on the busiest path in the system.
  • Reads need JOINs. To validate a spend you’d join transactions ⋈ outputs (and maybe inputs). JOINs mean touching multiple tables and indexes for one answer.
  • Deletion is a multi-table cascade. Removing one old transaction means cascading deletes across all those child tables via foreign keys.
  • More bytes in the write-ahead log. Everything is written durably first to a log (the WAL). More rows + in-place updates = more log bytes per transaction, and WAL volume is a first-class cost here.

How the folded, two-table design avoids each cost

DimensionNormalised (SQL store)This store (folded)
Rows per transaction1 + one per output + one per input + block links1 tx row (+ one spends row per spent output, later)
Big random-write indexestransactions PK + outputs PK + “unspent” index + …just two: the txs primary key and the spends uniqueness index

“Folding” in one line: instead of a separate row per output, a transaction’s outputs are packed into a few columns on the transaction’s own row (a flat blob of output IDs + small bitmaps + counts). The result: one read returns everything needed to validate a spend, and creating a transaction writes one row instead of many.

The payoff — and the price

Concretely (on a developer laptop, so treat as indicative, not production figures): the older normalised SQL store handles on the order of ~9,000 transactions/second; this store sustains roughly ~99,000/second while the sweeper and pruner run continuously and hold the table bounded — creation, spending, mining, stamping and reclaim all at once. Most of that gap is simply not paying the row-explosion and index-churn costs above; the rest came from measuring where the database spent its time (write-ahead-log volume per transaction, wasted shard probes) and removing each cost.

This is a deliberate trade, not a free win. Denormalising costs flexibility: you can’t easily run ad-hoc relational queries (“show me all outputs over 1 BSV”), the layout is special-purpose, and packing outputs into one row creates a ceiling for transactions with huge numbers of outputs (see §12). We accept those because this store isn’t a general-purpose database — it’s a purpose-built engine for one hot loop (validate spends, prune coins) where raw write throughput is everything.

12. How big can a transaction be? (size limits)

This store is tuned for ordinary transactions. It will still accept unusually large ones — up to some hard ceilings — but performance falls off well before those ceilings. Here’s exactly what limits what, and why.

The one rule that drives almost everything: in PostgreSQL, a single column value (one field in one row) can be at most 1 GB. This is a fixed, built-in limit — there is no setting to raise it. Two of this store’s columns can grow with the transaction, so they hit that 1 GB wall first.

The hard ceilings

WhatHard ceilingWhat sets it
Whole transaction size (serialized bytes) ~1 GB The entire transaction is stored in the raw_tx column. One field ≤ 1 GB, so a transaction whose serialized form is bigger simply cannot be inserted — the write fails. (The stored “extended” form is a bit larger than the wire form, so the real limit is a little under 1 GB.)
All script bytes (every input + output script, combined) fits inside that ~1 GB Scripts aren’t stored separately — they live inside raw_tx. So one giant script, or many big ones, are limited by the same ~1 GB transaction ceiling. There is no separate “max script size” in the store.
Number of outputs ~33.5 million Output IDs are packed into the single utxo_hashes field at 32 bytes each. 1 GB ÷ 32 bytes ≈ 33,554,432 outputs, then the write fails. (The matching spendable/frozen bitmaps are tiny by comparison, so utxo_hashes is what runs out first.)
Number of inputs no fixed field limit Inputs aren’t stored on the transaction’s row. Each input that spends a coin becomes its own row in the spends table. So input count is bounded only by (a) the ~1 GB raw_tx (which holds all the unlocking scripts) and (b) the practical cost of inserting that many rows — not by any single-field ceiling.
An output’s index (vout number) up to ~2.1 billion Stored as a 32-bit integer (prev_output_idx). Never the binding limit — you’d hit the 33.5 M output cap long before this.
Blocks a transaction is recorded in tens of millions The block_ids list. Normally 1 (a few across a reorg). Never a real concern.
The soft limits bite long before the hard ones. Because PostgreSQL can only read a big field all at once (it can’t fetch part of it):
  • Reading one output re-reads all of them. To check output #500,000 of a million-output transaction, the database must pull the entire utxo_hashes blob (here, ~32 MB) and the bitmaps. Spending such a transaction’s outputs one by one gets slower and slower (roughly quadratic). So the practical output limit is far below 33.5 million.
  • Reading one script re-parses the whole transaction. Output scripts/amounts come from raw_tx, so fetching any single output’s script means decompressing and parsing the entire transaction. Fine for normal sizes; expensive for multi-megabyte transactions.
In short: a near-ceiling transaction is stored correctly, just slowly. The design targets normal transactions.

Which PostgreSQL settings matter here

SettingEffect on this
The 1 GB field limitNot configurable. It’s compiled into PostgreSQL. You cannot turn it up to store a >1 GB transaction. The only way past it would be a schema change (e.g. splitting raw_tx into chunks) — not a setting.
block_sizeThe page size (default 8 KB), set when PostgreSQL is built. It does not change the 1 GB field cap — big values are moved out-of-line (“TOASTed”) automatically regardless of page size.
work_mem / maintenance_work_memMemory a query may use to build, sort, or aggregate values. Operations that materialise a huge output blob or many big rows need more; too little spills to disk and slows down.
shared_buffersThe cache. Large transactions evict more useful pages; a workload full of big transactions wants a bigger cache.
max_wal_size and WAL settingsEvery insert is written to the write-ahead log. A near-1 GB transaction produces a correspondingly large WAL record — worth accounting for in checkpoint/WAL sizing.
statement_timeoutA query that touches a giant row (or a huge spend batch) can take a long time; a tight timeout may cut it off.
Column STORAGE / COMPRESSIONControls how big values are stored and compressed. This store already sets raw_tx to LZ4 compression, which shrinks the on-disk size (and the effective room before the 1 GB wall) but doesn’t change the limit itself.
Want a smaller limit on purpose? The store doesn’t impose its own maximum — it accepts whatever it’s given, up to PostgreSQL’s ceilings. If a deployment wants to reject oversized transactions earlier (for safety or predictability), that cap belongs upstream (consensus/policy rules), before the transaction ever reaches the store — so a pathological transaction is refused cleanly rather than failing mid-insert at the 1 GB wall.
